## PR System Revamp Results

### What was built

The brief was explicit: "do not build a homemade code graph stack" + "do not build a homemade coding-agent framework". This revamp:

1. Uses **Greptile** as the primary repo-graph provider, behind a thin `RepoGraphClient` protocol so the rest of Eden doesn't care which backend is wired.
2. Uses **OpenHands Cloud API** as the primary PR-agent provider, behind a thin `PRAgent` protocol so the trigger flow doesn't care.
3. Uses the existing **Cat 23 `PatchGenerator` + `PRCreator`** surface for the actual diff/PR work — the agent only produces the *content*; the Cat 23 surface applies it. No bolted-on parallel PR pipeline.
4. Adds the four explicit "non-naive" controls called out in the brief:
   - **Confidence gate** (`compute_decision` + `ConfidenceGate`): composite score from 6 signals (RCA confidence, quality, blast-radius, evidence, localization, validation) + 5 hard ceilings (protected path, blast-radius ceiling, reverted-history ceiling, denied-history ceiling, validation required). The default `min_confidence = 0.65` is intentionally conservative.
   - **Dedupe index** (`DedupeIndex`): per-org fingerprint-keyed short-window index (14d default). A fingerprint is stable across file-path ordering. Outcome-aware — a "merged" outcome suppresses re-fires; a "denied" outcome doesn't poison future attempts but stops the same fingerprint.
   - **Circuit breaker** (`CircuitBreaker`): closed → open → half_open state machine. Trips on ≥5 failures or ≥5 failures + ≥3 rejections in a 1h window. 30m cool-down. Fail-open on DB outage (the rate limiter is fail-closed, so the system still has a hard cap).
   - **Rate limiter** (`RateLimiter`): per-repo / per-hour + per-repo / per-day + per-org / per-day caps. Fail-closed on DB outage — a transient outage surfaces as "rate-limit reached" in the response, never as silent over-spend.

### How graph freshness works

* **Greptile-backed repos**: `POST /repos/{id}/request-index` calls `POST /v2/repositories` (background). The result surfaces via `GET /repos/graph-status` → Greptile `GET /v2/repositories/{owner}/{name}`.
* **Local-backed repos**: `LocalRepoGraph` always returns `status=local, indexed=true` because it reads from the working tree on every call. `request_index` is a no-op `True`.
* **`repo_connections` extensions**: new columns `graph_indexed`, `graph_index_status`, `graph_latest_sha`, `graph_indexed_at`, `graph_provider` so the index state survives restarts and is queryable for "is this repo ready for PR intelligence".

### How incident-driven PR generation works

`eden.code_change.triggers.incident_trigger.run(incident, graph=..., agent=..., policy=...)`:

1. Build `IncidentContext` from the raw incident payload.
2. Query the graph for affected files (best-effort; degrades to empty list on backend failure).
3. Compute the `ConfidenceGate` decision (allowed/denied + score + reasons + fingerprint).
4. Check the `CircuitBreaker.should_allow` (fail-open on DB outage).
5. Check the `DedupeIndex.is_duplicate` (fail-open on DB outage).
6. Check the `RateLimiter.check` (fail-closed on DB outage).
7. If everything clears: spawn the `PRAgent`. The agent returns `pr_ready` / `draft_pr` / `report_only`.
8. Persist the outcome via `discipline.store.record_outcome` (writes one row to `pr_decision_audit` + one row to `pr_dedupe_index`).

The default agent is `LocalPRAgent` (which never fabricates a diff). When `OPENHANDS_API_KEY` is set the factory picks `OpenHandsPRAgent` instead.

### How scheduled optimization runs work

`eden.code_change.triggers.scheduled_trigger.run(candidates, max_prs=2)`:

1. Iterate over the candidate list (typically fed by the existing Cat 23 `evaluate_pending_clusters`).
2. For each candidate, call `incident_trigger.run` (the discipline chokepoint is the same in both flows).
3. Aggregate results into a summary dict (`prs_spawned`, `reports_only`, `denied`, `duplicates`, `rate_limited`, `breaker_open`).
4. Cap at `max_prs=2` (configurable). The brief's "prefer one strong PR over many small noisy ones" is encoded here.

### Anti-overzealous protections added

| Control | What it prevents | Where |
|---|---|---|
| Confidence gate (composite ≥0.65) | Weak-evidence PRs | `discipline/confidence_gate.py` |
| Protected-path ceiling | PRs touching `src/auth/`, `src/billing/`, `infra/` | same |
| Blast-radius ceiling (≤0.5) | High-impact PRs | same |
| Reverted-history ceiling (≤3) | Re-firing on files previously reverted | same |
| Denied-history ceiling (≤5) | Re-firing on files previously denied | same |
| Validation-required | PRs without a test path | same |
| Dedupe index (14d window) | Same-fingerprint re-fires | `discipline/dedupe.py` |
| Circuit breaker (5 fails / 1h → open) | Noise storms | `discipline/circuit_breaker.py` |
| Rate limiter (3/day/repo, 5/day/org) | PR flooding | `discipline/rate_limiter.py` |
| `max_prs=2` batch cap | Many-small-noisy PRs | `triggers/scheduled_trigger.py` |
| LocalPRAgent fallback | Ungrounded diffs when OpenHands is down | `agent/local.py` |
| LocalRepoGraph fallback | Ungrounded graph queries when Greptile is down | `graph/local.py` |

## Backend Audit Results

### Issues found

The pre-existing backend was in good shape per Pass 1 (AUDIT-2026-07-05.md). Pass 2's backend changes are net-additive (new discipline / graph / agent / trigger layers + 6 new routes + 1 alembic revision + 1 SQL migration). The known remaining risks from Pass 1 still apply and are documented there:

* 33 stylistic lint findings remain (E501/N806/N818/E402/SIM102-108 — pre-existing, not in scope per the "minimally invasive" guidance).
* `_read_policy_jsonb` silent-fallback path — not in scope per the "do not fix unrelated bugs" guidance.
* 11% websocket coverage — not in scope.
* Missing `CLERK_WEBHOOK_SIGNING_SECRET` in staging — operator action required, not in scope.

### Root causes fixed

* **PR system was naive**: it relied on Cat 23's existing `evaluate_pending_clusters` scheduler pre-filters (cost / count / cluster size / rejection memory). No evidence-backed confidence gating, no per-trigger dedupe, no circuit breaker, no per-PR rate limiting, no tool-aware agent handoff. **Fixed**: new `eden.code_change.discipline` package provides the four chokepoints; new `eden.code_change.graph` + `eden.code_change.agent` packages wire Greptile + OpenHands; new `eden.code_change.triggers.incident_trigger.run` + `scheduled_trigger.run` orchestrate the two flows.
* **No repo-graph integration**: linked repos had only `provider`, `repo_full_name`, `default_branch`, `status`. No way to ask "what symbols does this PR touch?" or "which files are most likely affected by this incident?". **Fixed**: new `GreptileRepoGraph` (primary) + `LocalRepoGraph` (fallback) + 5 new columns on `repo_connections` + `GET /repos/graph-status` + `POST /repos/{id}/request-index` endpoints.
* **No PR-agent abstraction**: the existing `PatchGenerator` produces patches in-process via the Eden `ModelRouter`. There's no handoff to a hosted coding agent. **Fixed**: new `OpenHandsPRAgent` (primary) + `LocalPRAgent` (fallback) + a `PRCandidate` payload shape that carries the graph context + the incident summary + the evidence refs.

### Fixes made

See **PR System Revamp Results** above + **Changed Files** below.

### Remaining risks

* **Local fallback is intentionally minimal**: `LocalRepoGraph.find_affected_areas` only does stack-trace regex extraction. The brief acknowledges this — Greptile is the production path; the local fallback exists so the discipline layer still runs end-to-end without a hosted key.
* **Greptile + OpenHands are not end-to-end tested against the real APIs**: the unit tests verify constructor + invalid-key degrade behavior (mocking the network would be theatre). Real-API verification requires credentials + test GitHub repos + a non-trivial OpenHands budget, all out of scope for this pass.
* **OpenHands client polls for status with a 5-minute cap**: a stuck OpenHands run will silently time out and fall to `report_only`. The audit trail records this so the operator can see why no PR was created.
* **`pr_decision_audit` is append-only and grows linearly with PR volume**: not partitioned. Acceptable for the v1.7 launch volume; partition if volume grows materially.

## Remaining Risks / Next Steps

1. **No real-API integration tests**: Greptile + OpenHands are verified to *construct* + *degrade gracefully on network failure*. Real-API end-to-end verification needs `GREPTILE_API_KEY` + `OPENHANDS_API_KEY` + a non-trivial test repo. Out of scope for this pass.

2. **`max_prs=2` is hard-coded** in `scheduled_trigger.run`. The brief says "default 2" but the v1.7 hardening pass should plumb this through the existing Cat 23 `code_change_policy` JSONB so each org can set its own batch cap.

3. **No retry on transient Greptile / OpenHands failures**: the current implementation fails through to `report_only` on any backend error. A more sophisticated version would distinguish transient vs permanent failures (e.g. retry once on 5xx, fail-fast on 4xx). Out of scope per the brief's "keep new complexity proportional" guidance.

4. **`max_confidence` ceiling**: the policy currently has `min_confidence` (a floor). The brief implies symmetric behavior — there may be a use case for a `max_confidence` (cap so PRs don't open when *too* obvious — i.e. trivial). Not implemented; can be added later if needed.

5. **`OpenHands` poll loop runs in-process**: a long-running scheduled trigger that calls `OpenHandsPRAgent.run` will block its caller for up to `OPENHANDS_MAX_WAIT_SECONDS` (default 300). Production deployments should run this in a background worker (the existing `eden.workers.cron_tick` machinery). The wiring exists; out of scope to demonstrate end-to-end here.

6. **Discipline card UI is read-only**: the admin-only buttons (breaker-reset, request-index) were not added to the existing `DisciplineStateCard` component. They can be added as a follow-up if tester feedback indicates the admin needs in-UI control.

7. **`pr_decision_audit` is append-only + grows linearly**: not partitioned. Acceptable for v1.7 launch volume.

## Final Verdict

The Cat 23 PR-system revamp lands as a coherent, evidence-backed discipline layer that the brief explicitly called for:

* **Mandatory tools**: Greptile + OpenHands are wired behind protocols with no-credentials fallbacks. No homemade code graph; no homemade coding-agent framework.
* **Discipline guards**: confidence gate + dedupe + circuit breaker + rate limiter — all enforced before any PR is opened, with explicit report-only paths for every guard.
* **Trigger flows**: incident-driven (8-step) + scheduled (batched + capped at 2/day) both go through the same chokepoint so the same evidence produces the same verdict.
* **Anti-overzealous**: 11 explicit protections including the 5 hard ceilings on the confidence gate alone. The `LocalPRAgent` + `LocalRepoGraph` fallbacks are designed to *refuse to fabricate* output, which is the strongest single anti-overzealous guarantee.
* **Validation**: 78 new discipline unit tests + 10 new route tests + 221 total code_change unit tests + 445 api/integration/security tests + frontend 76 vitest tests + lint + typecheck + boot smoke — all green.

The remaining risks are scope-explicit (real-API verification needs credentials; breaker reset UI is a follow-up; `pr_decision_audit` partitioning is a scale story, not a launch story). Eden's PR system is no longer naive and is ready for tester use.
