## Executive Summary

This pass was a coordinated body of work that delivered two things:

1. **PR-system revamp.** Eden's PR system moved from "fire patch on every incident" (the naive pattern the brief explicitly rejects) to a disciplined, evidence-backed pipeline with a multi-signal confidence gate, a per-org dedupe index, a circuit breaker, per-repo/per-org rate limiting, repo-graph integration (Greptile with a local fallback), and OpenHands-based PR-agent integration (with a report-only fallback). The pipeline ships *honest* report-only paths when evidence is weak — it never fabricates a diff.

2. **Stabilization pass.** Backend tests, lint (F821/F822/B904 critical rules), type checks (Python + TypeScript), frontend lint, and the frontend test suite all remain green. The discipline surface is wired into the existing Cat 23 route layer with 5 new endpoints + 1 frontend discipline-state card that surfaces the breaker / rate-limit / graph status inline.

## Backend audit results

### New: PR-discipline layer (`src/eden/code_change/discipline/`)

**What ships:**

- `confidence_gate.py` — :class:`ConfidenceGate` + :func:`compute_decision` (pure function) + :class:`Trigger` + :class:`Decision` + :func:`fingerprint_trigger`. Composite score is a weighted sum of RCA confidence (0.35), quality score (0.25), 1 - blast_radius (0.20), evidence count (0.10), localization (0.05), and validation (0.05). Hard ceilings (protected paths, blast radius, revert history, denied history, validation path) cannot be overridden by raising the score.
- `circuit_breaker.py` — :class:`CircuitBreaker` with closed / open / half_open state machine, configurable failure threshold + window + cooldown + min-rejections-to-trip. Fail-open on DB outage (the breaker is the "too many PRs" protection; failing open lets the rate caps decide).
- `dedupe.py` — :class:`DedupeIndex` keyed on the decision fingerprint, 14d rolling window, best-effort on DB outage (fails open so the gate still runs).
- `rate_limiter.py` — :class:`RateLimiter` enforcing per-repo-per-day (3), per-repo-per-hour (1), per-org-per-day (5). Fail-closed on DB outage (the limiter protects against over-spend; failing closed keeps the system safe).
- `store.py` — :func:`record_outcome` writes a structured audit row + appends to the dedupe index. Two best-effort writes per call.

**Why this matters:** The previous PR system had scheduler pre-filters (cost cap, file-path cooldowns, rejection memory) but no central decision point. The discipline layer replaces the ad-hoc checks with a single explicit chokepoint that both incident-driven and scheduled flows share — so the same evidence produces the same verdict in both contexts.

### New: Repo-graph layer (`src/eden/code_change/graph/`)

**What ships:**

- `protocol.py` — :class:`RepoGraphClient` + :class:`AffectedArea` + :class:`GraphQueryResult`. The Protocol every backend must implement.
- `greptile.py` — :class:`GreptileRepoGraph` (the primary, hosted path). Calls `POST /v2/repositories`, `GET /v2/repositories/{name}`, `POST /v2/query`. Best-effort: a non-2xx or timeout returns ``None`` / empty lists, never raises.
- `local.py` — :class:`LocalRepoGraph` (the no-credentials fallback). Reads from the local checkout via the existing :class:`LocalRepoProvider` + extracts stack-trace file paths + uses any ``file_path_hint`` from the incident payload.
- `factory.py` — :func:`get_default_repo_graph` selects Greptile when ``GREPTILE_API_KEY`` is set, local otherwise.

**Why this matters:** Per the brief, Eden must not build a homemade code graph. The repo-graph layer ships the Greptile integration with a sensible local fallback so the platform works without a hosted key. Both backends share the same protocol so the incident + scheduled triggers don't care which one they're talking to.

### New: PR-agent layer (`src/eden/code_change/agent/`)

**What ships:**

- `protocol.py` — :class:`PRAgent`. One method: ``async run(candidate, decision)``.
- `openhands.py` — :class:`OpenHandsPRAgent` (primary). Calls OpenHands Cloud API (``POST /v1/conversations`` + polls ``GET /v1/conversations/{id}`` until FINISHED or ERROR). Extracts the diff from the final assistant message via ``_extract_diff`` (regex over fenced ``diff`` / ``patch`` blocks). Returns ``{"kind": "draft_pr" | "pr_ready" | "report_only", "title": ..., "body": ..., "diff": ..., "conversation_id": ...}``. Honours "not code-fixable" phrases in the agent's response and downgrades to ``report_only``.
- `local.py` — :class:`LocalPRAgent` (no-credentials fallback). Returns a structured ``report_only`` payload with a markdown body summarising the evidence the gate saw. **Does NOT fabricate a diff** — the discipline layer's confidence gate is the only protection against ungrounded PRs, and an ungrounded agent output would bypass it.
- `factory.py` — :func:`get_default_pr_agent` selects OpenHands when ``OPENHANDS_API_KEY`` is set, local otherwise.

**Why this matters:** Per the brief, Eden must not build a homemade autonomous PR agent. The PR-agent layer ships the OpenHands integration with a local fallback that always reports (never opens an ungrounded PR).

### New: Trigger flows (`src/eden/code_change/triggers/`)

**What ships:**

- `incident_trigger.py` — :func:`run` orchestrates the incident-driven flow:
  1. :func:`gather_context` (sync; pure)
  2. Async graph query to enrich the context (when a graph client is provided)
  3. :func:`compute_decision` runs the gate
  4. Circuit breaker check (open → report-only with reason=circuit_breaker_open)
  5. Dedupe index check (duplicate → report-only with reason=duplicate_in_window + previous_outcome)
  6. Rate limiter check (over cap → report-only with reason=rate_limit + remaining_today)
  7. Gate decision (denied → report-only with reason=gate_denied + reasons list)
  8. Spawn the PR agent (or report-only when no key) — result is ``draft_pr`` / ``pr_ready`` / ``report_only``
  9. Persist the outcome via :func:`discipline.store.record_outcome`
- `scheduled_trigger.py` — :func:`run` orchestrates the daily optimization flow:
  1. Run the incident-trigger flow for each candidate concurrently
  2. Aggregate results
  3. Cap at ``max_prs`` (default 2) so we don't flood the org

**Why this matters:** The two flows share the same chokepoint. The scheduled flow is intentionally simpler because the existing Cat 23 surface (:class:`PatchGenerator` + :func:`scheduler.evaluate_pending_clusters`) already produces candidate lists; the discipline layer adds dedupe + gate + batching on top.

## PR system revamp results

### Repo-graph approach

- **Primary:** Greptile API. Activates when ``GREPTILE_API_KEY`` is set. Calls ``POST /v2/repositories`` (submit / re-index), ``GET /v2/repositories/{name}`` (status), ``POST /v2/query`` (query the indexed graph).
- **Fallback:** LocalRepoGraph. Uses the existing ``LocalRepoProvider`` + a stack-trace path extractor + a path-hint extractor. Answers the same 4 queries the Greptile client does.
- **Factory:** :func:`eden.code_change.graph.get_default_repo_graph` picks the right backend based on ``GREPTILE_API_KEY``.

### Graph freshness

- **On link:** The ``POST /repos/connect`` route triggers ``GreptileRepoGraph.request_index`` with ``background=True``. The store-side call is best-effort; the connection persists regardless.
- **On re-index:** The new ``POST /repos/{repo_id}/request-index`` endpoint kicks off re-indexing for a connected repo (admin-only).
- **Status read:** ``GET /repos/graph-status`` returns the latest indexed SHA + last_indexed_at for the org's active repo(s).
- **DB persistence:** The ``repo_connections`` extension adds ``graph_indexed``, ``graph_index_status``, ``graph_latest_sha``, ``graph_indexed_at``, ``graph_provider`` columns so the portal can show the index state without an extra round-trip to Greptile.

### Incident-driven PR generation

- **Trigger:** :func:`eden.code_change.triggers.incident_trigger.run` is the orchestrator.
- **Context-gathering:** :func:`gather_context` (sync, pure) + an async graph query for ``find_affected_areas``.
- **Discipline check:** Confidence gate → breaker → dedupe → rate limit. Any failure → ``report_only`` with a structured reason.
- **PR agent:** When all checks pass, :class:`OpenHandsPRAgent.run` (or :class:`LocalPRAgent.run` when no key) produces a ``draft_pr`` / ``pr_ready`` / ``report_only`` payload.
- **Output policy:** When the agent produces a diff, the default is ``draft_pr``. The caller can promote to ``pr_ready`` after running its own validation pass. When the agent says "not code-fixable" or produces no diff, the result is ``report_only`` with a reason.
- **Persistence:** Every outcome is written to ``pr_decision_audit`` + the dedupe index.

### Scheduled optimization PR generation

- **Trigger:** :func:`eden.code_change.triggers.scheduled_trigger.run` is the orchestrator. It expects a list of candidate dicts (same shape as the incident payload).
- **Batching:** The candidate list is gated through the incident-trigger flow concurrently; results are aggregated.
- **Cap:** ``max_prs`` (default 2) caps the number of PRs in one run. The brief's "prefer one strong PR over many small noisy ones" guidance.
- **Default categories:** reliability fixes, error handling improvements, missing retries / timeouts, performance improvements, instrumentation gaps, test coverage additions. The implementation accepts whatever categories the upstream scheduler emits.

### Anti-overzealous protections

The brief requires four layers of protection. All four are present:

1. **Confidence gate (per-org policy).** Multi-signal composite score with hard ceilings for protected paths, blast radius, revert history, denied history, and missing validation. Default threshold 0.65 — conservative.
2. **Circuit breaker (per-org).** Trips after 5 failures in 1h (configurable). Cooldown 30m. Resets on ``manual_reset`` (admin-only endpoint). Fail-open on DB outage (lets the rate caps decide).
3. **Dedupe index (per-org, 14d window).** When a fingerprint is seen recently with an active decision, the trigger returns ``report_only`` with ``reason=duplicate_in_window`` + the previous outcome.
4. **Rate limiter (per-repo + per-org).** Per-repo-per-day 3, per-repo-per-hour 1, per-org-per-day 5. Fail-closed on DB outage (the limiter protects against over-spend).
