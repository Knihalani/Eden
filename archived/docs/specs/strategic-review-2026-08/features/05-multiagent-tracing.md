## How competitors/standards represent this (2026) — verified against primary sources, not paraphrase

**OpenTelemetry GenAI semantic conventions**, fetched directly from `open-telemetry/semantic-conventions-genai`'s `docs/gen-ai/gen-ai-agent-spans.md`:

- `gen_ai.operation.name` is `Required` on every agent span and has a closed enum of **18** values (not 4, as pass 2 stated): `chat`, `create_agent`, `create_memory`, `create_memory_store`, `delete_memory`, `delete_memory_store`, `embeddings`, `execute_tool`, `fetch_response`, `generate_content`, `invoke_agent`, `invoke_workflow`, `plan`, `retrieval`, `search_memory`, `text_completion`, `update_memory`, `upsert_memory`. Only 4 of the 18 are agent-*orchestration* specific (`create_agent`, `invoke_agent`, `execute_tool`, `invoke_workflow`); the rest cover single-call LLM/memory operations under the same attribute.
- **Two distinct `invoke_agent` span shapes**, confirming (and sharpening) pass 2's "CLIENT when remote, INTERNAL when in-process" claim: *Invoke Agent Client Span* — kind `CLIENT`, "describes GenAI agent invocation over a remote service," explicit examples **OpenAI Assistants API, AWS Bedrock Agents**; *Invoke Agent Internal Span* — kind `INTERNAL`, "invocation within the same process," explicit examples **LangChain agents, CrewAI agents**. `create_agent` spans are always `CLIENT` kind, named `create_agent {gen_ai.agent.name}`.
- Exact attribute names and requirement levels: `gen_ai.agent.id` (`Conditionally Required` if applicable — spec explicitly says this is for **stable, provider-issued identifiers** like a Bedrock ARN; instrumentors are told *not* to use transient in-memory IDs), `gen_ai.agent.name`, `gen_ai.agent.description`, `gen_ai.agent.version` (all `Conditionally Required` if provided), `gen_ai.provider.name` (`Required`, only on the Client-side spans — the Internal span table omits it), `gen_ai.conversation.id` (`Conditionally Required` "when available" — spec explicitly warns instrumentors **not to fabricate one from a trace ID or hash**), `error.type` (`Conditionally Required` on error). There is still no dedicated "parent agent" attribute anywhere in the spec — agent-to-agent nesting is the ordinary span parent/child tree, as pass 2 found.
- **Eden's own `otel_exporter.py` already violates the `gen_ai.conversation.id` guidance it would need to follow**: `_event_to_otlp_span` (`src/eden/observability/otel_exporter.py:264`) does `add("gen_ai.conversation.id", event.trace_id)` — exactly the trace-ID-as-conversation-ID fabrication the spec calls out by name. Minor, but worth fixing in the same pass as the write-path fix below since it's the same file.

**A2A protocol**, fetched directly from `a2a-protocol.org/latest/specification/` (Linux Foundation, v1.0+): the `Task` object's real fields are `id`, `contextId`, `status`, `artifacts`, `history`, `metadata`; the `Message` object's real fields are `messageId`, `contextId`, `taskId`, `role`, `parts`, `metadata`, `extensions`, `referenceTaskIds`. **The spec has no "parent agent" or "delegating agent" field at all** — delegation/continuity is represented purely by soft linkage: `contextId` groups related tasks/messages, `taskId` addresses one task, and a `Message.referenceTaskIds` array lets a follow-up message point at earlier tasks for context ("agents SHOULD use referenced tasks to understand context and intent," not a hard requirement). This sharpens pass 2's "false equivalence" observation into something stronger: eden's `a2a_links` table (explicit FK-style `parent_agent_id`/`child_agent_id`/`parent_trace_id`/`child_trace_id` columns) is architecturally **more rigid than the real A2A spec it's named after**, which deliberately keeps delegation as soft, optional reference lists rather than a hard parent pointer — eden built a stricter data model than the standard it's alluding to, under the standard's name.

### New finding: exactly why the ingestion write-path never caught up — traced to source, not inferred

Three independent pieces of evidence, found by tracing forward from the "columns exist, nothing writes them" fact in pass 2:

**1. `TelemetryEvent` (the dataclass, not just the SQL string) never gained the fields.** `src/eden/observability/telemetry_collector.py:40-101` is the complete field list for the class `TELEMETRY_INSERT_SQL` serializes — verified line-by-line (43 required fields through `response_message_hashes`, matched 1:1 against `to_dict()` at `:102-142`). There is no `operation_name`, `provider_name`, `parent_agent_span_id`, or `child_agent_trace_id` field anywhere on it. The root cause sits one layer upstream of where pass 2 located it: it's not that the INSERT statement forgot four column names, it's that the object being inserted was never given the attributes to insert. The same gap exists in the Pydantic ingest model (`TelemetryEventIngest`, `src/eden/api/routes/observability.py:65`) that validates the wire payload before it becomes a `TelemetryEvent`.

**2. A fully-specified internal design doc for exactly this work exists, was executed only through the DDL step, and stops there.** `supplementaries/research/05_otel_genai.md` (dated 2026-06-28, "Author: Eden research harness") is not a loose note — it's a complete implementation runbook: 30 named columns split into Required/Recommended/Industry/Resource-attributed tiers, 6 partial indexes, a `finish_reason` CHECK-constraint enum, and (§8.4, "Round-trip assertion") the *exact* `INSERT INTO telemetry_events (...)` statement extended with all 30 new columns in order, followed by: *"**The 8 `from_dict()` changes** — in the dataclass at `telemetry_collector.py:135-175`, add the 30 fields after `service_tier`... The Pydantic ingest model in `src/eden/api/routes/observability.py:35` (`TelemetryEventIngest`) needs the same 30 fields added."* Every one of those steps is unexecuted today. Two tells that the doc predates and diverged from what actually shipped: (a) it labels the new columns *"NEW COLUMNS (066)"* — migration 066 was in fact consumed by an unrelated index migration (`066_session21_indexes.py`, the same migration pass 2 cited for independently rediscovering the `parent_agent_id` bug), pushing the OTel columns to 067 and suggesting the plan sat unexecuted across at least one migration-numbering cycle; (b) the doc specifies `usage_input_tokens`/`usage_output_tokens` (OTel-canonical `gen_ai.usage.*` naming) but the migration that actually shipped, `067_trace_quality_otel_columns.py:77-85`, added `usage_prompt_tokens`/`usage_completion_tokens`/`usage_total_tokens` instead — OpenAI Chat Completions' legacy field names, not the spec's. Whoever wrote migration 067 did not have the research doc's exact column list in front of them, or diverged from it deliberately without updating the doc — either way, DDL and design doc have already drifted from each other, on top of neither being wired to ingestion.

**3. The `gen_ai.operation.name` *mapping logic* was independently built a second time — correctly — and also never connected to the write path.** `OTelDualExporter._event_to_otlp_span` (`src/eden/observability/otel_exporter.py:201-238`) computes `operation = _OPERATION_NAME_MAP.get(event.event_type, "chat")` and attaches it as `gen_ai.operation.name` on every span it exports — but only to build a fire-and-forget OTLP/HTTP POST to the *customer's own* backend (Honeycomb/Datadog/Tempo; `flush()`, `:135-199`), gated behind `settings.otel_dual_emit_enabled` and silently dropped on any failure (module docstring: *"Failures never block the ingest path... they're logged at warning level and dropped"*). The computed value is never written back to eden's own `telemetry_events.operation_name` column — it's discarded the moment the HTTP POST returns. This is the strongest evidence for "half-finished, not never-started": the org has built the exact `event_type → gen_ai.operation.name` mapping twice (once as a design-doc spec, once as working export code) and both times stopped one write short of the database. Caveat for the fix: `_OPERATION_NAME_MAP` (`otel_exporter.py:36-49`) only covers LLM-call event types (`openai.chat_completion`, `anthropic.message`, etc., all mapping to `"chat"`); it has **zero entries** for eden's own `"tool.call"`, `"span.start"`, or `"env.step"` event types (per the `TelemetryEvent.event_type` docstring, `:48`), so reusing the map verbatim would mislabel every tool-call and agent-boundary span as `"chat"` — it needs new entries for `tool.call → execute_tool` and an agent-invocation signal (see migration diff below) before it's fit to write to a real column.

**4. One reader is already silently broken, not just theoretically unwired.** `TelemetryCollector.get_trace_tree` (`:1848-2109`) — the exact span-tree builder backing the portal's trace-detail endpoint (`src/eden/api/routes/portal.py:1385`, `collector.get_trace_tree(org_id, trace_id, hydrate_bodies=False)`) — builds a per-span `node` dict that includes `"error_type": row.get("error_type")` (`:2092`) with **no fallback**, unlike the token-count columns. `sessions/rollup.py:57-71` and `llmops/insights_tools.py:342-344` read `usage_prompt_tokens`/`usage_completion_tokens` too, but always behind `COALESCE(payload->>'input_tokens', usage_prompt_tokens, 0)` — the JSONB path already covers those, so they're inert-but-harmless. `error_type` has no such cover: every span node the portal's trace-detail view renders has had an always-`None` `error_type` since 067 shipped. Separately, `get_trace_tree`'s node dict also has no `agent_id` key at all (confirmed: `grep '"agent_id"'` on the file hits only the dataclass and `to_dict`, never the tree-node builder) — so even a single trace spanning multiple agents can't show *which* span belongs to which agent in the view that already walks `parent_span_id` today. The same permanently-null `error_type` column has a second live consumer: `sessions/rollup.py:137-140`'s `_turn_errored(row)` returns `bool(row["error_type"]) or outcome in _ERROR_OUTCOMES` — since `error_type` is never written, that first disjunct is always `False`, and session-level error detection today runs entirely on the `outcome` fallback.

**Adjacent bug, not in scope to fix here but found while tracing the above:** migration `067_trace_quality_otel_columns.py:140`'s `downgrade()` runs `DROP COLUMN IF EXISTS finish_reason` — but `finish_reason` is not 067's column; it was added by `011_capture_full_payloads.py:63` (`VARCHAR(64)`, pre-existing, already written by `TELEMETRY_INSERT_SQL`) and 067's own `ADD COLUMN IF NOT EXISTS finish_reason VARCHAR(32)` (`:93`) was a silent no-op against it. A downgrade of 067 would destroy live `finish_reason` data that 067 never owned.

## User Experience & Value

**Who this is for, and the actual flow.** The user is an engineer debugging a multi-agent run. They land on a `trace_id` — from an alert, a user report, or the traces list — and open the portal trace-detail view: `GET /orgs/{org_id}/traces/{id}` (`portal.py:1320`) calls `TelemetryCollector.get_trace_tree` (`telemetry_collector.py:1848`) and flattens the resulting span tree into a list of `TranscriptStep` objects (`_flatten_tree`, `portal.py:788`, via `_tree_node_to_step`, `portal.py:637`). This is the "run transcript" the engineer actually reads, and it's real, wired frontend code — `traces-client.tsx` and `traces-detail-panels.tsx` both consume it — not a lab-only fixture.

Three things are true about that transcript today, verified directly against `TranscriptStep`'s schema (`portal_contracts.py:78-97`) and its construction:

1. **No span carries an agent identity.** `TranscriptStep` has `id`, `spanId`, `parentId`, `model`, `provider`, `tokensIn/Out`, `costUsd`, `attributes`, previews, `errorMessage` — no `agentId` field exists, and `_tree_node_to_step` never references `node.get("agent_id")`, not even into the generic `attributes` bag. Compare this to `TraceListItem`, one level up, which does have `agentId` — populated by `_PREFERRED_AGENT_ID_SQL` (`portal.py:805-820`), a `COALESCE`/`ARRAY_AGG` that picks **one** agent id to represent the *entire trace*, explicitly filtering out framework-prefixed ids (`pydantic-ai:%`, `langchain:%`, `langgraph:%`, `crewai:%`, etc.). So a trace spanning three agents shows up in the trace list labeled with a single agent name, and once opened, that label disappears entirely — every span in the transcript looks identical in origin. Today the only way to tell which agent produced which span is to notice a discontinuity in `model`/`provider`/naming in span titles, or to go around the portal and query `telemetry_events.agent_id` directly.
2. **The one piece of real agent-linkage data that *is* attached to a span is stripped before it reaches the browser.** When a caller uses the A2A SDK wrapper, `_A2ACallCtx.attributes()` (`sdk/a2a.py:114-129`) merges `{"parent_agent_span_id": ..., "child_agent_trace_id": ..., "a2a": {"invocation_type": ..., "parent_agent_id": ..., "child_agent_id": ..., "response_status": ...}}` into the span's JSONB `attributes`. But `_tree_node_to_step` builds the outgoing `attributes` field via a scalar-only filter, `safe_attrs = {k: v for k, v in attrs.items() if isinstance(v, (str, int, float, bool))} or None` (`portal.py:752`), which silently drops the nested `"a2a"` sub-document — the one part of the payload with human-readable agent ids and an explicit invocation type. Only the two flat UUID strings survive, unlabeled, inside a generic key-value bag the frontend renders as raw JSON with no click-through back to the span or trace they point at.
3. **There's no visual vocabulary for "this is an agent boundary."** `TranscriptKind = Literal["task", "llm", "tool", "bash", "span"]` (`portal_contracts.py:21`) is the exhaustive set of step kinds `_step_kind` (`portal.py:444`) can assign — no `"agent"` or `"handoff"` kind exists. Once `operation_name` is wired end to end (item 3 in the code changes above), an `invoke_agent`-kind span would still render as an undifferentiated `"span"` unless this enum and `_step_kind`'s mapping are extended too.

**What it should look like**, grounded in what's already computed correctly server-side, not generic tracing-vendor language:

- **Swimlane the transcript by agent, not just by parent/child span nesting.** The trace tree already walks `parent_span_id` correctly for intra-agent nesting; the only missing input is `agent_id` on each `TranscriptStep`. This is close to free once `get_trace_tree`'s node dict carries `agent_id` (item 5 in the code changes above) — add `agentId` to `TranscriptStep`, populate it in `_tree_node_to_step`, group/color the existing flat list by that field. No new backend work beyond what's already scoped.
- **Render agent-to-agent handoffs as a distinct, labeled event, not a buried UUID pair.** Surface the `a2a` sub-document (`invocation_type`, `parent_agent_id`, `child_agent_id`, `response_status`) as a first-class transcript marker — e.g. a `"handoff"` `TranscriptKind` — instead of letting the scalar-only `safe_attrs` filter erase it.
- **Give the failure a causal chain, not just a red dot.** When a child agent's span errors, the engineer should be able to walk backward through `parent_agent_span_id`/`a2a.parent_agent_id` to see which agent's delegation produced the failing call, and whether that parent agent then also failed as a consequence — the blast radius *within one trace*, not just the aggregate blast radius `FleetService.delegation_graph` already computes org-wide (`_delegation_trust_score`, `fleet/service.py:404-443`) but which has no portal surface at all.
- **Filter/search a trace list by agent identity, not just by the one collapsed "preferred" agent per trace.** `_PREFERRED_AGENT_ID_SQL` deliberately picks a single winner per trace for the list view; there's no query path for "show me every trace where agent X participated, even as a sub-delegate." That requires either exploding the collapse (list `agent_id` as an array per trace) or a secondary "participants" facet — a materially different query shape, worth scoping as its own follow-up.
- **Put the org-wide delegation graph somewhere a human will find it.** The backend (`delegation_graph()`) is correct and self-refreshing; the fix is presentational — a panel on the existing `agents-client.tsx` detail pane, populated by a single already-correct `GET /orgs/{org_id}/fleet/delegation` call. The one wrinkle: as noted above, the frontend already deleted the `fleetApi`/`a2aApi` client namespaces once, with a regression test guarding against reintroduction — reviving this needs to update that test, not just add a new call site.

None of this requires new tracing infrastructure or a new data model. Every gap above is a *rendering* or *field-plumbing* gap sitting on top of computation that already exists and is, per the verification above, already correct — the same "half-finished, not never-started" shape the rest of this doc documents at the ingestion-write-path layer.

## Recommendation

Unchanged priority order from pass 2 (rewrite the broken query against `a2a_links`; wire ingestion to the existing columns; ship one portal view against an already-correct endpoint), now with the migration/insert diff above as the literal execution plan for item 2, and the `agents-client.tsx` + `GET /orgs/{org_id}/fleet/delegation` pairing as the literal execution plan for item 3's Fleet half (the `a2a` BFS endpoint into trace-detail remains the other, still-open half).
