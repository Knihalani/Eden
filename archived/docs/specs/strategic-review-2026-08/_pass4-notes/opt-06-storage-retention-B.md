# Pass 4 — Agent B (Impact Validator) notes on optimizations/06-storage-retention.md

## IMPACT AUDIT — is the storage cost/growth impact measured or asserted?

**Verdict: entirely asserted/estimated, never measured, and the doc's own labeling is honest about this.** There is no `$` cost figure anywhere for Eden's own storage, and no GB/byte-level number anywhere in the codebase for any of the 8 `DEFAULT_POLICIES` tables.

1. **No dollar figure exists in the doc for Eden's own infra.** `grep -n "\$\|USD"` over the doc returns exactly one hit (line 177), and it's a generic external quote from web research ("a snapshot with no expiry is a cost liability") — not an Eden-specific cost number. Confirmed via direct grep.

2. **`get_storage_summary()` (the one storage-visibility function in the codebase) only returns row COUNTs, not bytes/GB, and only for 3 tables.** Read directly at `src/eden/data_platform/storage_lifecycle.py:525-541`: `count = await client.fetchval(f"SELECT COUNT(*) FROM {table}")` for `["usage_events", "silver_events", "quarantine_events"]` only (line 536). No byte-size, no cost calculation exists anywhere in `data_platform/` or `storage/`. This independently confirms the doc's own claim at its line 130 ("`get_storage_summary()`... doesn't track `checkpoint_blobs`, `trace_replay_sessions`, `replay_sessions`, or any of the 6 no-op-policy tables"). Since no other size-tracking mechanism was found in a repo-wide grep for `bytes_used|table_size|pg_total_relation_size|storage_cost`, the doc is correct that no ground-truth size/cost signal exists for eden to have cited even if it wanted to.

3. **The doc's one quantified growth number is explicitly self-labeled "Illustrative" and is a post-launch hypothetical, not a measurement of the actual dead-policy impact.** Doc lines 82-89 ("Growth estimate" section): "~1,300 rows/month, ~1-2 MB/month" for `trace_replay_sessions` is modeled by analogy to LangSmith/Honeycomb/Sentry adoption patterns (web research), not derived from any Eden telemetry, log, or dashboard data. This is appropriately hedged in the doc's own prose ("Illustrative low/mid case") — not a false claim — but a reader skimming the "Growth estimate" section header could mistake it for a measured number. Worth a synthesis note that this is model output, not observed data.

4. **The illustrative model's core input ("20 active orgs") is not reconciled against Eden's actual measured production scale, which is available elsewhere in the repo and is more than 2x smaller.** `src/eden/workers/cron_tick.py:80-81`: "Measured on production that day, with **9 orgs** and ZERO user telemetry in the previous 24h" (dated 2026-07-29, independently cited in `optimizations/05-cron-jobs.md:151-153`). The 06 doc never cites or checks its "20 active orgs" assumption against this real figure. This doesn't make the estimate "false" (it's an aspirational/future-state model, not a claim about today), but it is a missed grounding opportunity — the doc had access to a real number and didn't use it. Flagging as a NEW FINDING below rather than a CUT, since the estimate is still explicitly hypothetical.

5. **No current size/growth number is given for any of the 6 no-op policies' actual tables**, even the 2 that have real backing tables (`user_feedback`, `quarantine_events`). The `quarantine_events` "currently-confirmed live unbounded-growth mechanism" claim (doc line 129) is **verified true** by direct read of `src/eden/data_platform/silver_etl.py:774-778` (unparseable rows kept, never deleted) and `:797-803` (`fully_inserted = bool(parsed_ids) and report.silver_inserted >= len(events)`; deletion only on full success) — but the doc gives no row count or rate for how big this table actually is today. This is a real, verified qualitative gap; it's just not quantified, and nothing in the repo would let it be quantified without an ops-side query.

**Net for synthesis:** the doc does not overclaim a dollar/GB impact — it correctly declines to invent one and is explicit about which numbers are modeled vs. observed. The main risk is a reader mistaking the "Growth estimate" section for a measurement. No CUT needed on this axis, just a calibration note for synthesis.
