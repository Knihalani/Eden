## USER EXPERIENCE & VALUE (draft — Agent B going deeper)

**Who actually touches this subsystem, and what do they experience?**

- **End customers of eden's guardrails REST API** (`POST /orgs/{org_id}/intelligence/guardrails/evaluate` and siblings) are the only real user of `evaluate_and_act`. Today that's a *very* small population: zero SDK wrapper means every caller is hand-rolling an HTTP integration against the raw endpoint — this is Lakera-Guard-shaped ("call our endpoint yourself") but without Lakera's marketing/docs muscle behind "here's the one endpoint you need." The realistic user journey is: an eden customer builds an agent, wants basic PII/injection protection, discovers `/guardrails/*` exists (how? — no SDK surface, so likely via reading OpenAPI docs or Postman-style API exploration), and wires it in manually per-call.
- **The trap in that journey is exactly the bypass finding**: the single most natural thing a customer integrating guardrails would do is pass their trace_id — it's the one piece of context they already have on every call if they're also using eden for tracing/observability (which is eden's primary product surface). Doing the "obviously correct, best-practice" thing (correlate your guardrail check to your trace) is precisely what silently defeats the check. This is close to a worst-case UX trap: it doesn't fail loudly, it doesn't fail for the naive integration (someone who *doesn't* bother threading trace_id through gets the real engine), it fails for the *diligent* integration. A customer who read eden's tracing docs carefully and did the "right thing" architecturally is the one most likely to get burned.
- **Value proposition erosion**: eden's pitch for this subsystem (per "What already exists") is a mature, fail-closed engine — genuinely a differentiator versus doing nothing. But the value only materializes if a customer (a) discovers the endpoint exists at all (no SDK, no doc pointer confirmed in this repo scan), and (b) either never passes `trace_id` or is aware enough of this collision to route around it deliberately. Net: the subsystem's *architecture* is worth more than its *current realized value to any actual integrator*, because the one on-ramp (raw REST call) is both hard to discover and, once discovered, has a landmine in the most natural usage pattern.
- **Portal users get zero value from this at all today** — confirmed above the portal's guardrails UI is a read-only policy viewer over fixture data for parts of it and a live `GET .../policies` call for the rest; there's no in-portal way to *test* a policy against sample text, see a live intervention log entry render, or diagnose why a given trace's guardrail check did or didn't fire. An org admin staring at `GuardrailMetrics.dashboard`'s near-zero `total_interventions` counter (per doc's finding, item 4/72) has no UI affordance to figure out whether that means "we're safe" or "the checks aren't running" — the dashboard actively misleads by omission, and there's no drill-down to disambiguate.
- **Promotion loop (`EvalToGuardrailLink`) has real potential value** (turning a judge's confirmed-bad pattern into an enforced policy) but its UX-facing trigger (confirm/dismiss in some judge-review UI) wasn't traced in this pass — worth Agent B independently confirming whether that promotion flow is reachable from any actual UI or is API-only like `evaluate_and_act` itself, since if it's also API-only, "value" here means "value to a customer who writes code against our promotion endpoint," not "value a portal user gets by clicking a button."
- **Competitive positioning (from doc's benchmark table)**: eden covers the *shape* of Lakera/Bedrock/NeMo's category list but every detector is v0-heuristic. For UX purposes the more relevant gap than raw detection quality (which Agent B should weigh independently) is that competitors ship this as a wrapped, default-on part of the request path (Bedrock's `ApplyGuardrail`, parallel evaluation with no bypass branch) — eden ships the equivalent of the *engine* but leaves the *integration effort and the not-getting-silently-bypassed effort* entirely on the customer.
