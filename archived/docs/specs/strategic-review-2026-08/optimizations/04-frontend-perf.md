# O4 — Portal Frontend Performance

Framework (verified against `clients/portal/package.json`): Next.js `16.2.10` (Turbopack dev / webpack prod build — see below), React `19.2.7`, `@tanstack/react-query@^5.100.14` for data fetching, `@tanstack/react-virtual@^3.13.12` for list windowing, `recharts@^3.9.1` for charts. Bundle discipline is **already set up and enforced in CI**: `bun run analyze` (`ANALYZE=true next build --webpack`, `package.json:25`), `bun run check:bundle` → `scripts/check-bundle-size.sh:16-17` (`PER_CHUNK_MAX_BYTES=400*1024`, `TOTAL_MAX_BYTES=6*1024*1024`, comment: "Largest observed ~327 KB; total ~6 MB"), and a dedicated webpack `cacheGroup` for `recharts`/`victory-vendor`/`d3-*` (`next.config.ts:21-46`) because Turbopack was duplicating the ~412KB recharts bundle per async island — the config comment at `next.config.ts:18-20` says this explicitly, and it's why prod builds still opt into webpack via `--webpack` in the `analyze`/build scripts rather than Turbopack. Most of the "generic" frontend-perf checklist (heavy chart libs, bundle budgets, chunk-size gates) is already handled and CI-gated here, not just present.

## Worst offender: issues kanban board and session-turn timeline render fully unvirtualized, despite virtualization being the established, working pattern one directory over

**The gap is real, precisely located, and cheap to fix** — the tooling, the memo pattern, and a shared virtualization wrapper already exist in this exact codebase; nothing here requires new infrastructure.

**The working reference implementation** — `clients/portal/src/app/(portal)/traces/traces-client.tsx`:
- Import: `import { defaultRangeExtractor, useVirtualizer } from "@tanstack/react-virtual";` at `traces-client.tsx:15`, plus a shared helper `import { measureVirtualRow, VIRTUAL_SCROLL_ATTR } from "@/lab/virtual-list";` at `traces-client.tsx:16`.
- Usage: `const feedVirtualizer = useVirtualizer({ ... measureElement: measureVirtualRow, ... })` at `traces-client.tsx:848-858`, consumed via `{feedVirtualizer.getVirtualItems().map((item) => { ... ref={feedVirtualizer.measureElement} ... })}` at `traces-client.tsx:1121,1130`.
- The shared helper it uses, `clients/portal/src/lab/virtual-list.ts` (40 lines total), exports `VIRTUAL_SCROLL_ATTR` (`:17`, a marker attribute `vitest.setup.ts` uses to fake a viewport under jsdom so virtualized lists are actually exercised in tests, not silently rendered empty) and `measureVirtualRow` (`:29-40`, a `measureElement` wrapper that refuses a zero-height reading and falls back to `estimateSize` — without it, a pre-paint measurement of 0 would collapse `getTotalSize()` and make the virtualizer's range calculation cover the *entire* list, silently defeating windowing). This is a genuinely engineered, test-covered virtualization utility, not a bare library call.
- Rows are memoized: `RunListButton = memo(...)` (`clients/portal/src/lab/lab-ui.tsx:177`); the traces detail panel also memoizes its own row types, `TranscriptRow = memo(...)` (`traces-client.tsx:697`) and `ParallelGroupRow = memo(...)` (`traces-client.tsx:782`).

**The unvirtualized offenders:**
1. `clients/portal/src/app/(portal)/issues/issues-client.tsx` — the issues kanban board. `COLUMNS.map((col) => { const items = byColumn[col.id]; ...` at `:694`, and inside each column, `{items.map((issue) => (<li key={issue.id}><IssueRow issue={issue} active={...} onSelect={() => selectIssue(issue.id)} /></li>))}` at `:704-709` — plain, real DOM `<li>` nodes for every issue in every non-empty column, no windowing. Same file, `:349` (`runs.map((trace) => ...)`, the issue-detail "Runs" tab listing linked traces) is also unvirtualized, though bounded by however many traces are linked to one issue (typically small).
2. `clients/portal/src/lab/traces-session-lens.tsx` — the N12 session-turn timeline. `{apiTurns.map((turn) => (<li key={...}><TurnCard turn={turn} count={count} onOpenTurn={onOpenTurn} /></li>))}` at `:312`, and the pre-timeline-API fallback path `{fallbackTurns.map((turn) => { ... })}` at `:320`. Both plain `<ul>`/`.map()`, no windowing.
3. **The session-turn case is structurally worse than the issues case**, because it has **no server-side cap at all**. Traced through `clients/portal/src/lab/traces-session-lens.tsx:242-247` (`useOrgQuery` hitting `GET /orgs/{org}/sessions/{id}/timeline`) → `src/eden/api/routes/sessions.py:263-279` (`sessions_timeline` → `get_session_timeline`, no `limit`/`Query` param on the route at all) → `src/eden/sessions/timeline.py:170-208` (`get_session_timeline`): `trace_ids = summary["trace_ids"]` is every trace ID ever recorded for the session, and `turn_rows = await client.fetch(_TURNS_SQL, org_id, trace_ids)` fetches and returns all of them, unbounded. A long-running agent session (hours of tool-calling loops, or a support-bot session open for days) has no upper bound on turn count, and every one of those turns becomes a full `TurnCard` DOM subtree with zero windowing. Contrast with issues (server-capped at 200, see below) and traces (server-capped at 200) — the session timeline is the only list in the audited surface with *no* cap in either direction, client or server.

**Memoization gap compounds it:** `IssueRow` (`issues-client.tsx:79-115`) is **not** wrapped in `memo`, unlike its declared "sibling" `SessionListButton` in `traces-session-lens.tsx:77-91` (doc comment literally says *"Memoised sibling of `RunListButton` — same stable-callback contract"*, confirmed verbatim at `:76`). Worse, the call site passes a fresh inline closure every render — `onSelect={() => selectIssue(issue.id)}` at `issues-client.tsx:709` (`IssueRow`'s prop type is `onSelect: () => void`, confirmed at `:86`) — so wrapping `IssueRow` in `memo` alone wouldn't help; `selectIssue` is already a stable `useCallback` (`issues-client.tsx:565-571`), so the correct fix mirrors `SessionListButton`'s own pattern one file over: `handleClick = useCallback(() => onSelect(session.id), [onSelect, session.id])` (`traces-session-lens.tsx:87-90`) — pass `issue.id` + `selectIssue` down and let each row derive its own stable callback, instead of allocating one per row per render. `TurnCard` (`traces-session-lens.tsx:136`) is *already* `memo`-wrapped, so the session-timeline fix is "add windowing" only, not "add windowing + memo."

**Practical impact:** every keystroke in the issues search box (`issues-client.tsx:653-660`, controlled `query` state) recomputes `filtered`/`byColumn` (`:533-563`, correctly `useMemo`'d — the computation itself isn't the problem) and then re-renders every currently-mounted `IssueRow`, which absent virtualization is every issue in the response. The backend caps that response at `limit: int = Query(50, ge=1, le=200)` (`src/eden/api/routes/portal.py:1599-1601`, `list_portal_issues`), but the client never sends `limit` at all — `portalApi.issues` is `(orgId) => fetchApi<IssueFixture[]>(portalPath(orgId, "issues"))` (`clients/portal/src/lib/api/portal.ts:86-87`), no query params — so it always gets the server default of 50 and there is no "load more." **Correction to a claim in the original draft of this doc:** the backend does *not* actually expose `offset` as a client-controllable parameter — `list_portal_issues` hardcodes `IssuesRepo().list_issues(org_id, limit=limit, offset=0)` (`portal.py:1609`; grepped the whole file, no `offset: ... = Query(...)` exists for this route). So "wire up pagination" for issues is not purely a frontend fix. It does, however, need less new plumbing than it might appear: `IssuesRepo.list_issues` already accepts an `offset: int = 0` kwarg at the repo layer (`src/eden/issues/repo.py:270-277`) — only the route needs a new `offset` (or cursor) `Query` param threaded through to that existing repo parameter before the client can page past the newest 50/200.

**A third, smaller instance of the same pattern**, found while grepping more broadly (not part of the original two): `clients/portal/src/app/(portal)/signals/signals-client.tsx:862` (`{filtered.map((signal) => (<SignalRow .../>))}`, `SignalRow` defined at `:55`, not memoized) renders the signals list unvirtualized too. The backend query here is `SELECT ... FROM nl_signals WHERE org_id = $1 ORDER BY updated_at DESC LIMIT 200` (`src/eden/api/routes/portal.py:2016-2024`) — hardcoded `LIMIT 200`, no `Query` param, no client-side paging possible even in principle. Lower priority than issues/timeline (200 rows of short text is meaningfully cheaper to paint than 200 rich `IssueRow`s or an unbounded turn list), but the same "reuse `useVirtualizer` + `memo`" fix applies if it's ever addressed.

**A fourth instance, added in the most recent portal commit** (`953286b7`, "session timeline UI, automations tab, saved views"), postdating this doc's earlier drafts: `clients/portal/src/app/(portal)/signals/automations-panel.tsx:489` (`{automations.map((automation) => (<li key={automation.id}><AutomationRow .../></li>))}`, `AutomationRow` defined at `:51`, not wrapped in `memo`). Backend: `GET /automations` (`src/eden/api/routes/wave6_online.py:209-215`) takes `limit: int = Query(100, ge=1, le=100)`, and `AutomationsEngine.list_automations` (`src/eden/automations/engine.py:29-46`) hard-caps at `min(int(limit), 100)` with a plain `ORDER BY updated_at DESC LIMIT $2` — no client-side pagination control beyond the 100-row cap. Same fix pattern, even lower priority than signals (100-row cap vs. 200, and automations are typically small, admin-configured lists in practice) — noted for completeness, not urgent.

This is an inconsistency, not a missing-capability gap: the `useVirtualizer` pattern, the `memo` convention, and a shared, test-covered virtualization helper (`lab/virtual-list.ts`) already exist in this codebase and are proven correct in `traces-client.tsx`. The fix in all three cases is "reuse what's already there," not new infrastructure or a new dependency.

## Concrete DOM-cost estimates for the three unvirtualized lists (Phase 3)

Row-level element counts, counted directly from each component's JSX (not estimated from category norms):

- **`TurnCard`** (`traces-session-lens.tsx:136-217`) — baseline card (has an `outcome`, no stumble badges, no linked issues): `li` → `div` → `div.flex` → `span` (index/count) → `SeverityBadge` (1 element) → `button` (trace id) → `span` (duration) → `p` (cost line, +1 `span` separator, +1 more when `outcome` is present) → `p` (summary) = **~11 real DOM nodes/card**. Each stumble kind adds one more `span` (`:186-193`) and each linked issue adds one more `Link` (`:198-206`) — a card with 2 stumble badges + 1 linked issue is ~15 nodes.
- **`IssueRow`** (`issues-client.tsx:79-115`, wrapped in an `li` at the `.map()` call site, `:704-709`) — `li` → `button` → `div` → `div.flex` (`SeverityBadge` + `IssueStatusChip` + `span` occurrence count) → `p` (title) → `p` (agent/lastSeen) = **~9-10 real DOM nodes/row**, fairly constant (no conditional sections).
- **`SignalRow`** (`signals-client.tsx:55-90`) — same shape as `IssueRow` (`button` → `div` → `div.flex` with two `StatusChip`s + `span` → `p` → `p`) = **~10 real DOM nodes/row**.

Worst-case row counts, from the actual server-side caps (or lack thereof):

- **Kanban (issues)**: server-capped at `limit: int = Query(50, ge=1, le=200)` (`portal.py:1599-1601`). Worst case is all 200 concentrated in one column (e.g. triage backlog stuck in "Open") → **200 × ~10 ≈ 2,000 DOM nodes**, +~10 for the 3 column wrappers/headers. Bounded and modest in absolute terms even at the cap.
- **Signals**: hardcoded `LIMIT 200` (`portal.py:2016-2024`, no client control). Same arithmetic → **200 × ~10 ≈ 2,000 DOM nodes**. Same order of magnitude as kanban.
- **Session-turn timeline**: no cap anywhere (see below), so the row count is genuinely open-ended rather than a fixed worst case. Grounding it in something concrete rather than "unbounded" as a qualitative label: the feature's own spec anticipated this — `docs/specs/features/n12-session-multiturn-timeline-ui.md:218` lists **">50 turns → virtualize horizontal scroller"** as a designed *degradation mode*, and the Test plan / Acceptance criteria sections (`:176`, `:186`) only ever validated against a **20-turn session** (`p95 <800ms`), not against anything near what the data model actually allows. A turn is one finalized trace (`sessions/rollup.py` docstring: "Runs once per `trace.finalized` message... unit of work is one *session*"); nothing in `SessionRollupIndexer._session_trace_ids` (`rollup.py:267-291`) or `LIVE_WINDOW_S = 300.0` (`timeline.py:29`) caps how many finalized traces can accumulate into one `session_id`. There is no in-repo turn-cadence statistic or telemetry to derive a precise worst-case row count from, so the following is **illustrative arithmetic, not a measured figure**: a single autonomous agent (coding/ops loop, or a support session literally left open for days, both explicitly the scenario this doc already names) producing one turn every ~30s for 24 hours would be ~2,880 turns, and at ~11-15 DOM nodes/card that's on the order of tens of thousands of DOM nodes for one page load — an order of magnitude past the kanban/signals worst case (~2,000 nodes each at their server caps), and, unlike those two, it keeps growing with session age instead of being capped. The load-bearing, independently-verified fact is simply that no server-side cap exists at all for this endpoint — the specific node-count multiplier is a plausibility illustration on top of that fact, not evidence in itself.

## Session-timeline pagination: exact backend parameter and the matching frontend change

**Backend** — `sessions_timeline` (`sessions.py:264-270`) needs the same two `Query` params its sibling route already has two functions above it in the same file, `sessions_list` (`sessions.py:234-241`): `limit: int = Query(50, ge=1, le=200)`, `offset: int = Query(0, ge=0)`, passed through to `get_session_timeline(org_id, session_id, limit=limit, offset=offset)`.

Inside `get_session_timeline` (`timeline.py:170-208`) the naive fix — slicing `trace_ids[offset:offset+limit]` before querying — is **wrong**: `trace_ids` is not chronologically ordered. Traced through `SessionRollupIndexer._session_trace_ids` (`rollup.py:267-291`): it's built as `dict.fromkeys(list(known) + [r["trace_id"] for r in indexed])`, where `indexed` comes from `SELECT DISTINCT trace_id FROM telemetry_events WHERE tenant_id = $1 AND session_id = $2` — **no `ORDER BY`**. Chronological order only exists after `_TURNS_SQL`'s `GROUP BY trace_id ORDER BY min(timestamp)` (`rollup.py:49-85`) runs. So the correct page boundary has to be applied to the query, not the array: append `LIMIT $3 OFFSET $4` to `_TURNS_SQL` itself (it's an f-string-safe plain `SELECT`, and Postgres can push the limit through the existing `ORDER BY` on the grouped output), still passing the full `trace_ids` array into `WHERE trace_id = ANY($2::text[])` as today. Then derive `page_trace_ids = [r["trace_id"] for r in turn_rows]` from the *paginated* result and use that (not the full session `trace_ids`) as the input to `_TURN_STUMBLES_SQL` and `_TURN_ISSUES_SQL` (`timeline.py:39-53`) — today both scan every turn in the session on every fetch; scoping them to the page turns them into page-sized queries too. Finally, `enumerate(turn_rows, start=1)` (`timeline.py:210`) needs to become `enumerate(turn_rows, start=offset + 1)` so a card's displayed `{turn.index}/{count}` stays stable across pages instead of restarting at 1 each time. No response-shape break is needed: `SessionTimelineResponse.turn_count` (`sessions.py:207`) already carries the session's *total* turn count independent of `len(turns)`, so the frontend already has what it needs to compute "page N of M" without a new field.

**Frontend** — `sessionsApi.timeline` (`resources.ts:4370-4374`) currently takes only `(orgId, sessionId)` and sends zero query params, unlike its sibling `sessionsApi.list` immediately above it in the same object (`:4354-4368`), which already builds a `URLSearchParams` from `limit`/`offset`. It needs the identical treatment. Then `SessionTurnsSection` (`traces-session-lens.tsx:226-317`), which currently does a single non-paginated `useOrgQuery(timelineKey, orgId, () => sessionsApi.timeline(orgId!, session.id))` (`:242-246`), needs to become a `useInfiniteQuery` (React Query is already a portal dependency, `@tanstack/react-query@^5.100.14`) with `initialPageParam: 0`, `queryFn` passing `offset: pageParam`, and `getNextPageParam` comparing accumulated turns fetched so far against the response's `turn_count`. The `<ul>` at `:311-317` then needs a trigger to call `fetchNextPage()` — either a "load more" sentinel, or, once paired with the virtualization fix from the section above, the `useVirtualizer` range can drive it directly (fetch the next page when the visible range approaches the end of what's loaded), the same pairing `traces-client.tsx`'s feed virtualizer is positioned to model if it turns out to page too (not verified this pass — worth checking next).

## Third finding: the trace-tree endpoint ships five span fields its only frontend consumer never reads

Broader sweep for large-payload responses (not list rendering): `TelemetryCollector.get_trace_tree` (`src/eden/observability/telemetry_collector.py:1848-2075`), served at `GET /orgs/{org}/observability/traces/{trace_id}/tree` (`observability.py:601-629`), builds **every** span node with `metrics`, `attributes`, `payload`, `request_body`, `response_body`, `reasoning`, `tool_calls_full`, and `tool_results` (`telemetry_collector.py:2044-2075`) — even on the **default, "cheap" path** (`hydrate_bodies=False`, the route's actual default at `observability.py:606`, described in the docstring as what "portal list-detail" uses). The cheap path only skips message-store reconstruction and zstd-decompressing the *body* columns; `reasoning`, `tool_calls_full`, and `tool_results` still fall through to raw row values (`row.get("reasoning")`, `row.get("tool_calls_full") or []`, `row.get("tool_results") or []`) and are never stripped from the response regardless of the flag.

The portal has exactly one consumer of this endpoint: `resources.ts:1263-1273` (`getTraceTree`, comment: "used by the Inspector page to render the call-graph view"), which feeds `lib/observability/build-transcript-rows.ts`. Grepped that file directly for every field it reads off each span `node`: it uses `node.metrics`, `node.payload`, `node.attributes` (`:46-48`, token/cost aggregation) and derives its *own* `request_body`/`response_body`/`tool_results` from **inside** `node.payload` (`:182,201,216` — `payload.request`, `payload.response ?? payload.output ?? payload.content`), not from the API's top-level `request_body`/`response_body`/`tool_calls_full`/`tool_results`/`reasoning` fields. Those five top-level fields are grepped nowhere else in `clients/portal/src` outside this one file that doesn't use them. For a trace with a long reasoning chain, large tool outputs (RAG documents, big API responses), or verbose request/response bodies, this multiplies the `/tree` response size by however large those blobs are — per span, for every trace-tree fetch — for a field set the frontend silently discards. Fix: have `get_trace_tree` omit `request_body`, `response_body`, `reasoning`, `tool_calls_full`, and `tool_results` from the node dict when `hydrate_bodies=False` (they're already conditionally computed only when `True` for `request_body`/`response_body`; the other three just need the same guard), and only fetch/return them on a dedicated per-span "expand" call if the Inspector ever needs drill-down bodies.

## Secondary finding: agent detail page fetches the whole org's recent trace list to filter client-side for one agent

- `clients/portal/src/app/(portal)/agents/agents-client.tsx:361-374` — `tracesQuery = useOrgQuery(..., () => portalApi.traces(orgId!), SHELL_QUERY)` fetches the org-wide, unscoped, most-recent-50/24h trace list (`src/eden/api/routes/portal.py:1183-1200`, `list_portal_traces`, defaults `window="24h"`, `limit=50`), then does `const fromApi = (tracesQuery.data ?? []).filter((t) => t.agentId === agent.id)` (`:368-370`) to derive `runs` for a single agent. The inline comment at `:360-361` ("Prefer React Query traces for this page — catalog alone was empty when /agents did not prefetch traces") shows this was a deliberate workaround for a different bug, but it means every agent-detail page view pays for and discards traces belonging to every other agent in the org, and an agent whose activity is older than the org's most-recent 50 traces will render an empty run list even though data exists for it — there's no agent-scoped, paginated backend call being used here even though `list_portal_traces` already accepts `limit`/`window` query params that this call site simply never sets. Fix: pass an `agent_id` filter (would need adding to the route/repo query, since `list_portal_traces` currently has no agent-scoping parameter at all — confirmed by reading the full signature at `portal.py:1186-1192`) or, short of a backend change, at minimum widen `limit`/`window` for this specific call site so agent-detail doesn't silently under-report older agents.

## Recommendation (priority order)

1. **Virtualize the two worst offenders** using the existing `lab/virtual-list.ts` helper + the `useVirtualizer` pattern already proven in `traces-client.tsx`:
   - `issues-client.tsx`'s kanban columns (`:694-716`) — straightforward, since each column is already a bounded, keyed list.
   - `traces-session-lens.tsx`'s turn list (`:312`, `:320`) — higher priority than it looks, because this is the only list in the audited surface with **no server-side cap at all** (see above); a long session can currently ship an unbounded DOM tree to the browser today, not just be slow to search.
   Also wrap `IssueRow` in `memo` and replace the inline `onSelect={() => selectIssue(issue.id)}` closure with a `useCallback`-derived stable handler, mirroring `SessionListButton`'s `handleClick = useCallback(() => onSelect(session.id), [onSelect, session.id])` (`traces-session-lens.tsx:87-90`). Low effort, no new dependency, directly reuses in-repo precedent on both counts.
2. **Add a server-side cap to the session timeline endpoint** (`src/eden/api/routes/sessions.py:263-279` → `src/eden/sessions/timeline.py:170-208`) — today `get_session_timeline` has no `limit`, unlike every other list endpoint touched in this review (issues capped 200, traces capped 200, signals capped 200). This is a small backend change but it's the actual root cause of the timeline's unbounded-worst-case; frontend virtualization bounds the *rendering* cost but not the *payload/fetch* cost of a session with thousands of turns.
3. **Add an agent-scoped, paginated traces query** for the agent-detail "Runs" panel (`agents-client.tsx:361-374`) instead of filtering the org-wide 50-trace list client-side — needs a small backend addition (`list_portal_traces` currently has no `agent_id` param) plus the client-side call-site change.
4. **Wire pagination for the issues list, route first.** Contrary to this doc's earlier draft, the backend route does *not* already support `offset` — `list_portal_issues` hardcodes `offset=0` (`portal.py:1609`). The repo layer, however, is already ready: `IssuesRepo.list_issues` accepts an `offset: int = 0` kwarg today (`src/eden/issues/repo.py:270-277`), so the fix is scoped to adding an `offset`/cursor `Query` param to the route and threading it through to the existing repo call, then having `portalApi.issues` / `lib/api/portal.ts:86-87` pass `limit`/`offset` and the client add "load more" — otherwise any org with more than 50 issues silently only ever sees the newest 50, with no user-visible signal that older issues exist.

## What "good" looks like elsewhere, for calibration

Web research on 2026 practice for data-dense dashboards (see Sources) converges on a small number of load-bearing patterns, all of which are either already true of eden's portal or map directly onto the fixes above:

- **Virtualize anything over ~100 rows.** The 2026 library landscape has shifted toward `@tanstack/react-virtual` (headless, pairs with TanStack Query/Table — eden's exact stack) and `react-virtuoso` (richer built-in variable-height/grouping support) over the now-maintenance-mode `react-window`. Eden is already on `@tanstack/react-virtual` and has a working, test-covered reference implementation in-repo (`traces-client.tsx` + `lab/virtual-list.ts`) — the issue is inconsistent application, not a wrong library choice or missing capability.
- **INP, not LCP/CLS, is the 2026 metric that matters for interaction-heavy dashboards**, and the highest-leverage fixes are structural (route-level code splitting, list virtualization) rather than scattered `memo`/`useMemo` calls — which matches this doc's priority ordering: virtualization first, micro-memoization (the `IssueRow`/closure fix) second because it's cheap but secondary to the windowing gap.
- **Granular Suspense boundaries / parallel Server Component data fetching** is the recommended 2026 Next.js pattern for multi-panel dashboards (each panel fetches independently so total wait is the slowest panel, not the sum). Eden's portal doesn't use per-panel RSC Suspense boundaries — it uses a coarser but still-parallel pattern: server-side `dehydrate*` functions batch each page's shards with `Promise.allSettled` + a page-level timeout budget, then hand off to one client component that owns rendering (see "already fine" section above). This is a reasonable, already-parallel middle ground for an app that's predominantly client-rendered post-hydration (heavy interactivity, live-updating lists, client-side filtering) rather than a candidate for an urgent rewrite — flagged here for awareness, not as a recommendation to restructure.
- **The generic principle** — bound DOM node count to the viewport regardless of dataset size — is standard practice for this category of UI (trace/event-list dashboards) and is exactly what's missing from eden's kanban board and session timeline today.
