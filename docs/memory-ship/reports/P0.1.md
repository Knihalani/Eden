## What changed

- **The plugin now works when installed.** Claude Code runs an installed plugin from a copy in `~/.claude/plugins/cache/<marketplace>/eden-memory/<version>/`. The hook's relative import of Eden's code could never resolve from there.
  - Before, every hook of an installed plugin spawned `eden hook` (p50 2650 ms, and the spawn started `hookd`). Without `eden` on `PATH`, it printed `{}`: memory silently off.
  - Now the hook finds the checkout in order: the checkout the plugin directory sits in (`--plugin-dir`, the harness), then `EDEN_ROOT`, then the directory marketplace the copy was installed from (Claude Code's `known_marketplaces.json`). It loads the memory hook in-process from the checkout's real path.
- **No slow fallback.** The plugin no longer calls `hookd` over HTTP (8 s timeout, with its key) or spawns `eden hook` / `bun cli.ts hook` (8 s timeouts, about 2.6 s each).
  - When Eden cannot load, the hook exits 0, prints nothing (it used to print `{}`), and appends the cause once to `$EDEN_HOME/plugin-fallback.jsonl`. "Once" is per cause; the line holds no prompt text.
  - `hooks.json` runs `bun --no-install`. Without it, a checkout lacking `node_modules` made Bun auto-install `@eden/ir` from the npm registry: a network call on a hook path, 390–750 ms per failed import. The base plugin did the same.
- **`eden doctor --memory`** (also part of the full `eden doctor` letter). It prints one line per check and exits 0 only when every line is ok:
  - `memory`: the memory hooks registered. The plugin is now detected from `installed_plugins.json` and the layered `enabledPlugins`. The old directory walk counted a disabled or merely downloaded copy as registered.
  - `plugin`: which copy Claude Code runs, whether it is enabled, and whether it equals the plugin directory of the checkout it loads Eden from; if not, it names `claude plugin update`.
  - `modules`: the installed copy's Submit command, run as Claude Code runs it (3 fresh processes, a throwaway Eden home). Ok when Eden loads in-process and the median is ≤ 150 ms. A copy from before P0.1 cannot report a fallback, so doctor refuses to vouch for it.
  - `fallback`: the causes the plugin logged.
  - `repo key`, `scope catalog`, `guard`: the store's keying today: per Claude session, no folder scopes, no policy guard. P0.5, P3.1 and P2.3 fill these in (follow-ups).
- **`scripts/fresh-clone-check.ts`**: clones a commit outside any repo with an empty `HOME` and checks, in order:
  1. the fallback before `bun install`;
  2. `bun install` and the CLI;
  3. the hook in place;
  4. the copy a real `claude plugin install` makes;
  5. `eden doctor --memory`.
  It needs the network (bun) and `claude`, so it is a slice tool, not a CI step.
- **Dead tests decided** ([P0.1-dead-tests.md](P0.1-dead-tests.md)):
  - 23 of the 32 quarantined `test.failing` tests are applied: 20 deleted (19 pin behaviour the spec drops or supersedes, 1 duplicate) and 3 fixed. That closes #18, #39, #54, #59, #60 and #61.
  - The four removed env knobs are gone from the READMEs.
  - The 9 tests of `src/memory-subagent.test.ts` (#64) are decided but **not applied**: the deletion was refused by a permission check (Not done).
- **Each test runs once.** The six `benchmarks/memoryagentbench/memory-*.test.ts` shims only re-imported `src/` tests, which `scripts/test.sh` already runs. Base run 37315872489 counted 40 tests twice; P0.0d's run counted 58 twice.
- **Plugin 0.2.0**, so installed copies pick up the new hook through `claude plugin update`.

## Decisions made

- **D20's Unix socket is not built** (D20; ROADMAP P0.1: "the plugin's fallback chain obeys the 150 ms budget (no 8 s fetch/spawn timeouts on Submit)").
  - D20's target is "a Unix socket first (5 ms connect, 100 ms total), then in-process", and the daemon "is never required". P0.1 removes the daemon from the plugin's chain instead of moving it to a socket. That keeps D20's binding part: no path exceeds the 150 ms Submit budget.
  - Why:
    - today's only daemon, `hookd`, serves `respondToHook` (tool-trace recording and transparent tool replacement), not the memory hook the plugin runs in-process;
    - a long-lived daemon serves old code after an update;
    - the in-process path measures inside the budget without one (below).
  - D20's text stays. The P6.2 follow-up builds the socket if the warm-daemon experiment needs the plugin to reach a daemon.
- **Finding the checkout of an installed copy.**
  - The plugin reads Claude Code's own record of a directory marketplace (`<claude>/plugins/known_marketplaces.json`, `installLocation`), located from the copy's path (`cache/<marketplace>/<plugin>/<version>`). That file is Claude Code's, not a documented interface. If its format changes, the hook logs "no Eden checkout … (tried: …)" once, and `eden doctor --memory` names it; `EDEN_ROOT` is the documented override.
  - Order: the plugin's own checkout before `EDEN_ROOT`, the old plugin's precedence. A worktree's `--plugin-dir` then runs that worktree's code.
- **Fail open means printing nothing** (CLAUDE.md "Fail open"; EXECUTION §5 fail-open contract). The old fallback printed `{}`.
  - The in-process path still prints `{}` when it has nothing to say, as before: P0.8's flag work owns that output.
  - `hooks.json` keeps its `|| echo '{}'`, which only runs when `bun` itself fails (P0.8 follow-up).
- **"Logs once" is once per (plugin copy, cause).** Two hooks failing at the same instant may both append the cause; `eden doctor` counts distinct causes. A logged cause stays visible, but its line is ok once the probe shows the hook loads again.
- **Doctor's `modules` verdict includes the budget**: the median of 3 fresh runs, the first one cold, ≤ 150 ms. One run is noisy, so `doctor-memory.test.ts` checks that the verdict matches the printed time rather than a fixed outcome; CI runners may be slower.
- **Doctor compares an installed copy with the checkout that copy loads Eden from**, not with the doctor's own checkout: the skew that matters is between the copy's scripts and the memory hook they load.
- **`repo key`, `scope catalog`, `guard` print today's state** (per-session store, none, off) rather than computing D1's repo key ahead of P0.5. Each later slice fills in its line (follow-ups).
- **Six shims, not three.** The P0.0d follow-up named `memory-{char,ranker,struggle}`. `memory-{encode,order,persist}` follow the same pattern; in base run 37315872489 it was that trio whose pairs were split.
- **Dead tests**: per test, with the spec row each decision rests on, in [P0.1-dead-tests.md](P0.1-dead-tests.md).
  - Ambiguous cases, resolved towards DECISIONS:
    - char :216 and :227: verbatim `[rule]` text against D14's rewording;
    - lanes :352: an identifier-shaped token admitting an episode is P4.3's (A7 §4), not the ICL lane's;
    - ranker :215: kept, as a fix; ranker :223: deleted, D17.
  - env-docs is fixed in the docs, not by restoring the knobs. Restoring them would contradict D1 (agent/project isolation), D17 (a fixed relevance floor) and "prints nothing on error" (a stderr swallow print).
- **The red tests changed in the implementation commit**:
  - the logged plugin path is compared by real path (macOS `/var` → `/private/var`);
  - the doctor test's `modules` verdict is read from its printed time;
  - one case was added: a pre-P0.1 copy is not vouched for.
  None of these weakens what the red commit asserted.

## Verification notes
