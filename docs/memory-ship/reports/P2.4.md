# P2.4 — Recurrence → pin; user-global proposal

**Outcome:** merged. A policy said unqualified in 2 sessions becomes a pin at sleep, and SessionStart briefs only pins: a rule said once and every intent are no longer briefed there. A pin held in 2 repos is proposed once for all projects. The user keeps it with "yes, everywhere", and from then on every repo is briefed it `(all projects)`, and the guard and the Submit trigger read it. `policy-recur` turns green, and every other arm keeps its record.
**PR:** #136 (predicted; see the PR page) · **Merge commit:** see PROGRESS · **Date:** 2026-10-12

## What changed
- **Recurrence → pin (D9; A4 §6, §7).**
  - Sleep's full pass (`consolidate`, which the idle sleeper runs) marks a policy a pin (`p` on its rule ref) when it was said unqualified in ≥ 2 sessions.
  - Rules are compared by `ruleIdentity`, so "never squash" and "never force-push" are two rules.
  - Sessions are counted from each row's `ep`, plus the new `eps`. The store keeps identical text as one row, so a session that types a rule again word for word is recorded on that row. A re-read, or a fork's copy of its parent's line (same uuid), is not counted.
  - Only statements still in force count. An intent never promotes.
  - Explicit `never` / `always` and "remember that …" stay pins from their first session, as before.
- **SessionStart briefs pins only (A4 §5.2).**
  - A rule row is briefed by its pinned clauses. A rule on no action class is briefed as before.
  - Session gists lose their rule clauses, so a rule reaches SessionStart only as a pin.
  - D23's ≤ 3 cap, scope and `Updated:` items stay P2.5's.
- **`policy_recur` (A4 §7)** is logged in the human Submit's wide event. It lists the prompt's unqualified policies that a live row of another session states.
- **The user-global store (D11, A4 §1 `<root>/_user/`, `src/memory-user-global.ts`).**
  - `policies.jsonl` holds policies only, never an intent or a fact. Rows are tagged `all-projects` and briefed `Rule you set: … (all projects)`.
  - **Proposal.** The idle sleeper's sleep reads every repo's rule index. A rule that is a pin, and in force, in ≥ 2 repos is proposed once. A SessionStart of a repo holding the pin shows it once, in place of the pin's bullet: `Proposed for all projects: … (say "yes, everywhere" to keep)`.
  - **Confirmation.** Only an affirmative "yes, everywhere" keeps it: a sentence of its own, in the repo that showed it, in that session or the repo's next one, within 7 days.
  - **D11's phrases** keep a typed policy directly: "in all / any of my projects", or "everywhere" / "globally" set off as the rule's last or first words. So does `eden memory remember --global`.
  - **Readers.** The guard, the Submit trigger and SessionStart read the user-global rules under one cid, `_user/P:…`. A repo row gives way to a global rule that is still in force in its repo: it loses that rule's clauses and keeps the rest of what it says.
  - **Leaving.** An opposite or a revocation holds in its own repo only, through that repo's validity. Said with D11's phrase, or "that rule is gone" after the guard asked, it moves the rule to `_user/history.jsonl`.

## Decisions made
- **Promotion runs in the full sleep** (`consolidate`, which the idle sleeper runs), and the proposal right after it (`sleepStore`). A4 §6 puts both in the heavy tier, which is not built (P3.4's follow-up).
- **D9 over A4 §7 (DECISIONS wins).** Promotion needs the policy unqualified in ≥ 2 sessions. A4 §7's `policy_recur` also fires when the earlier session said it as an intent, so it is logged but does not promote.
- **Word-for-word restatement.** The store keeps identical text as one row (seen-text dedup), so recurrence is recorded on the row (`eps`), not as a second row. A re-read, or a line with the row's own uuid (a fork's copy), is not a new statement.
- **A proposal is shown only in a repo holding the pin.** A repo without the rule never learns it before the user agrees, which `policy-recur`'s `third-repo-gets-it` also asserts.
- **The confirmation is an answer, not a phrase (review round 1).**
  - It needs an affirmative ("yes/yep/sure/ok, everywhere" or "keep it everywhere") as a sentence of its own.
  - It counts only in the repo that showed the proposal, in that session or the repo's next one, within 7 days.
  - The arm itself answers more than a day after the showing, so the session rule is the real bound and 7 days is a backstop.
- **"Everywhere" / "globally" count only when set off** as the rule's last or first words. In testing, "Never install packages globally" (npm's `-g`) had been kept for all projects. Only "in all / any of my projects" ends an object's noun phrase, so that rule keeps its old key (`dependency|neg|package-globally`, identical to `main`).
- **Removal scope (review round 1).** Writing to user-global needs an explicit phrase or a confirmation, so removing it everywhere does too. A plain opposite or revocation holds in its own repo, because each repo reads the global rules through its own validity. With D11's phrase, or "that rule is gone" after the guard asked about the rule, it moves to `_user/history.jsonl`.
- **A repo row gives way to a global rule only while that rule is in force in its repo** (review round 2), and keeps whatever else it says.
