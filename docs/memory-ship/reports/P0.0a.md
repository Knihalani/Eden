# P0.0a — Harness: Claude-shaped event + transcript simulator, process-per-event runner

**Outcome:** Merged. The memory program now has a Claude Code simulator: it replays R6-shaped sessions through a plugin's real hooks, one process per hook, with payloads that match real Claude Code 2.1.285 key for key. The canonical session through `plugins/eden-memory` runs 70 hook processes, all exit 0, and two fresh runs agree. Before, the long-horizon bench called `openMemory()` in one process and could emit no hook event.

## What changed

- **A Claude Code session simulator** (`benchmarks/memory-long-horizon/harness/`). It drives a plugin's real hooks the way Claude Code does. Before it, the long-horizon bench called `openMemory()` in one process and emitted no hook payload.
  - **Payloads.** All 13 hook events the memory design uses (A5 §3.1, plus PostToolUse and SessionEnd), field for field and in field order, as Claude Code 2.1.285 sends them. The reference is a capture from real sessions, not the docs alone (see Decisions).
  - **One process per hook.** Each matching handler of each event runs in a fresh process, matched by the plugin's `hooks/hooks.json` under the documented matcher rules, with the payload on stdin. Handlers of one event run in parallel. A batch of Reads fires its PostToolUse hooks concurrently, as Claude Code does.
  - **The real transcript format.** Line kinds, field order and `parentUuid` chains, from this machine's transcripts. It covers typed, queued and mid-turn prompts, task notifications, peer messages, tool calls and results, `hook_additional_context` and `queued_command` attachments, rewinds (append-only branches), `compact_boundary` with its summary, and subagent transcripts with their meta files. Lines reach the file after their step's hooks ran, because the real file lags (R0 F8); `--flush eager` writes them at once.
  - **Hook answers act on the session.** Contexts are saved as attachments where Claude Code puts them. A prompt that UserPromptSubmit blocks is erased and its turn does not run. A denied or declined tool call does not run. PreCompact can block compaction.
  - **R6-shaped sessions.** A seeded generator writes a session as a plain-data script, and a player replays it. Its shape follows R6 (A5 §3.8): human prompts per session, about 1.7 non-human submits per human prompt, a rewind in 27% of sessions, about 8 subagent windows per session, R6's per-turn tool calls, and compaction at 600k tokens.
  - **`replay.ts`** runs one session through a plugin and prints a JSON summary: events per point, exit codes, fail-open counts, latency, contexts, transcript size, and a digest that two runs of one script must share.
  - **Isolation.** Every run lives in its own directory. Hooks get `HOME`, `EDEN_HOME` and `EDEN_MEMORY_DIR` inside it, and inherit nothing from the caller except `PATH`, `TMPDIR` and `LANG`.
- **No product code changed.** Outside `harness/`, the diff is one line in the root `tsconfig.json` (`benchmarks/memory-long-horizon` is now typechecked) plus docs.
- **R0 gains four verified hook facts (F31–F34)**, from the capture. The one later slices most need: compaction fires a SubagentStop for an internal agent with `agent_type: ""` (F32).

## Decisions made

- **The reference is real payloads, not only the docs.** A5 §3.1 asks for payloads "exactly as in R0". R0 lists fields, but not their order or when optional ones appear. So the fixtures are the key lists of 23 payload shapes, recorded by a probe plugin in two real Claude Code 2.1.285 sessions on this machine, plus the line keys of this machine's transcripts.
  - Keys and formats only, so no transcript text enters git. Secret scan: 0 hits. One false positive was avoided by renaming a key, see Verification notes.
  - The rules this gave are now R0 F31–F34. For example, `permission_mode` is on UserPromptSubmit but `effort` is not; `prompt_id` is absent until the process's first prompt; `/compact` fires a SubagentStop for an internal agent with `agent_type: ""`.
- **Two deviations from the captured resume-then-compact order**, both asserted in `fidelity.test.ts`:
  - (a) The capture has a second `InstructionsLoaded(session_start)` just before PreCompact, when `/compact` ran in the resumed `-p` process. The simulator does not fire it, because one capture cannot say when it happens in general.
  - (b) After compaction the simulator fires `InstructionsLoaded(compact)`, per the docs ("re-loaded after a compaction event"). The captured process ended right after PostCompact, so the capture neither confirms nor refutes it.
- **Concurrency follows what Claude Code did.** The captured debug log shows two Bash calls from one message dispatched one after another. So a batch runs its calls one by one, unless every call is a Read, which runs concurrently, as R0 F11 describes. Several Agent calls in one batch are not modelled concurrently.
- **Background subagents are split into launch and completion.** Launch is PreToolUse(Agent), SubagentStart, PostToolUse(`async_launched`), PostToolBatch. Completion is the body, then SubagentStop, then the task notification. So Stop's `background_tasks` lists the subagent in between. Its events are serialized with the main thread's, not interleaved.
- **Unverified texts, kept short and labelled in the code:**
  - the refusal texts for a hook `deny`, a `defer`, and an `ask` in `dontAsk` mode (the decline text is verbatim from this machine's transcripts);
  - `hookName` on a tool-event context attachment (the event name, as observed for UserPromptSubmit and SessionStart);
  - where a SubagentStart context lands in the child transcript (after the task prompt);
  - the compact summary's wording after its first sentence;
  - the async-launch text, which is truncated.
- **Peer messages.** UserPromptSubmit receives `<agent-message from="…">…</agent-message>`, the form of the real `queued_command`, while the transcript line carries Claude Code's preface (observed). The live payload for an idle peer message was not captured (R0 F34).
- **Hook environment.** Hooks get a minimal environment (PATH, TMPDIR, LANG, the Claude Code variables, and HOME, EDEN_HOME and EDEN_MEMORY_DIR inside the run dir), not the caller's whole environment. This keeps runs reproducible and isolated, as CLAUDE.md requires. Real Claude Code passes its full environment.
- **Unmodelled handler features are refused at load**, not run differently: `if`, `async`, and non-command handler types. P2.3 needs `if` and will extend the runner.
- **A timeout kills the hook's process group.** The docs say Claude Code "cancels" the hook. Killing the group keeps a child such as `sleep` from holding the pipes open, which otherwise hung the runner. The payload is passed as a buffer, because a hook that exits without reading a large stdin otherwise stalled the write (found in review of my own code; regression test added).
- **Generator calibration came after the pre-registration, against its fixed bands.** The bands are R6's measurements and were not edited.
  - The first parameters missed 2 bands: human-prompt median 4 and max 29, because mid-turn prompts were drawn per batch; tool calls per turn p50 25.
  - The second missed 1 (p50 19). The third met all 6.
  - The modelled splits are named in `shape.ts`: subagents cluster in 35% of turns; 88% run in the background; 0.25 peers per turn; 20% of non-human submits arrive mid-turn; 8% of Bash calls fail.
- **The canonical session** is R6's shape with every feature switched on and tool calls scaled to 0.15, so a CI run takes about 7 s per replay. It uses seed 2043: of the first 3,000 seeds with every feature, the one whose ratios were nearest R6 (8 subagent windows; 8 non-human submits for 6 human prompts).
