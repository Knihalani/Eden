## 8. `next/dynamic` failed-chunk-load behavior for the 3 most user-critical call sites — traced through actual Next.js/React library source, not speculation

Section 6 flagged 18 `next/dynamic` call sites with no explicit error/retry UI as "latent." The 3 most user-critical are the trace/session detail panels in `clients/portal/src/app/(portal)/traces/traces-client.tsx`: **`SessionReader`** (`:95-101`, the session-transcript reader — mounted whenever a user opens a session from the traces list, `:1184-1188`), **`RunTranscript`** (`:89-93`, the default "trace" tab shown for every trace detail view, `:1512-1526`), and **`TreePanel`** (`:103-107`, the "tree" tab, `:1561-1566`). All three share the identical `{ loading: () => panelFallback }` option with no `ssr: false` and no error handling — but their *precise* production failure mode had not been traced past "no explicit error/retry UI" in prior passes. Traced it fully this pass by reading `next/dynamic`'s actual implementation (`node_modules/next@16.2.10/dist/shared/lib/lazy-dynamic/loadable.js`) and React's actual `lazy()` implementation (`node_modules/react@19.2.7/cjs/react.development.js`):

1. **`next/dynamic` in this Next.js version is a thin wrapper around `React.lazy` + `React.Suspense`**, confirmed directly in `loadable.js`: `const Lazy = React.lazy(() => opts.loader().then(convertModule))`, and because `loading` is always provided for these 3 call sites, `hasSuspenseBoundary = true`, so `Wrap = Suspense` with `fallback={<Loading .../>}` (i.e. `panelFallback`, the "Loading…" text). This is a real Suspense boundary, not a bespoke retry/loading component — meaning React's actual error-propagation rules for `lazy()` apply.
2. **`React.lazy`'s internal state machine (`lazyInitializer` in `react.development.js`) permanently caches a rejection.** `payload._status` starts at `-1`; the loader (`import()`) is invoked exactly once, the first time the component renders. On success, `_status` becomes `1` and the resolved component is returned on every subsequent render. **On rejection, `_status` becomes `2` and `payload._result` is set to the `Error`; from that point on, `lazyInitializer` skips re-invoking the loader entirely (`if (-1 === payload._status)` guards the fetch) and every single subsequent render unconditionally does `throw payload._result`.**
3. **A thrown (not pending-promise) error is not caught by the local `Suspense` boundary** — Suspense only catches thrown thenables for the pending state; a genuine `throw` propagates up to the nearest React error boundary. The nearest one here is `clients/portal/src/app/(portal)/error.tsx` (confirmed via `find src/app -iname "*error*.tsx"` — note the wildcard is required to match `global-error.tsx`'s non-exact basename — → only `global-error.tsx`, `(portal)/error.tsx`, `(marketing)/error.tsx` exist; there is no nested `traces/error.tsx`, and `grep -rln "ErrorBoundary\|componentDidCatch\|getDerivedStateFromError" src` finds no custom boundary anywhere in the app). This section's mechanism claims (the `loadable.js`/`lazyInitializer` trace above) were verified line-for-line against the actual installed `next@16.2.10` and `react@19.2.7` source in this pass — not inferred from documentation or paraphrase — so the "dead retry button" conclusion below is stated with full confidence, not as a plausible inference.

**What a user concretely sees, precisely, if `SessionReader`'s, `RunTranscript`'s, or `TreePanel`'s chunk fails to load in production** (e.g. a stale client after a deploy requests a JS chunk hash that's been evicted from the CDN/edge cache): a brief "Loading…" flash (the Suspense fallback, ~1 render), then **the entire traces page is torn down and replaced by the portal's generic `(portal)/error.tsx` screen** — "Something went wrong", the raw `error.message` (something like `Failed to fetch dynamically imported module` or a `ChunkLoadError`-style string — not a friendly, contextual "the trace viewer failed to load" message), and "Try again"/"Home" buttons. This is **not** "infinite spinner" (the framing in section 6) and **not** silent/console-only — it's a full-page crash-to-error-screen with a technical message, one level worse for the user (loses the whole traces workspace, not just the panel) but at least visibly surfaced rather than silent.

**Crucially, "Try again" does not work for this failure class.** `reset()` (wired to the button in `error.tsx:31`) re-renders the segment, but per point 2 above, the `RunTranscript`/`SessionReader`/`TreePanel` `Lazy` objects are module-scoped singletons created once when `traces-client.tsx` is first evaluated — their `_status` is already permanently `2` (rejected) in the running JS heap, so `lazyInitializer` will `throw payload._result` again immediately without ever re-attempting the `import()`. The user is caught in a loop: click "Try again" → same page → immediate re-crash, because the underlying rejected-promise cache never resets. **The only actual recovery path is a hard browser reload** (fetching a fresh JS bundle re-evaluates the module and creates a new, unrejected `Lazy` payload at `_status: -1`). No hint of this is surfaced anywhere in the UI — "Try again" visually implies it should work and silently doesn't. This is a materially different (and more actionable) finding than "latent, low-probability, spins forever": the failure mode is a full-page crash with a dead retry button, for 3 of the app's highest-traffic detail views.

## 9. Type-cast sweep (`as unknown as`, `as any`) — one systemic, real "unverified contract" pattern; no new isolated bugs

Grepped all non-test `.ts`/`.tsx` under `clients/portal/src` for both `as unknown as` and `as any`.

- **`as any` / bare `: any` annotations: zero hits anywhere in non-test source** (`grep -rn "as any\b"` and `grep -rn ": any\b|<any>|any\[\]"` both return nothing). Clean signal — the codebase does not use the bluntest type-safety escape hatch at all.
- **`as unknown as` — 24 non-test call sites, two distinct patterns, both intentional rather than marking a broken contract**:
  - 17 of them in `src/lib/api/resources.ts` (`:2987`-`:4520`) are all the identical `(api as unknown as Record<string, unknown>).xApi = xApi;` — a deliberate pattern for attaching sub-namespaces onto a shared `api` object after its static type has already been declared. Consistent, self-contained, not covering for a real mismatch.
  - The remaining 7 span two purposes: `src/lib/analytics.ts:97` and `src/lib/api/core.ts:128/222/241` (4 sites) are browser-feature-detection casts (`window as unknown as { plausible?: ... }`, `AbortSignal as unknown as {...}`) — needed because the installed TS lib doesn't type an experimental/optional browser API; the other 3, `src/lib/api/core.ts:413/489/492`, are the raw/SSE/blob response-widening casts detailed in the next bullet. Neither category is a broken-contract marker, just narrow, justified escape hatches.
- **The one genuinely worth flagging is systemic and not a single cast**: `src/lib/api/core.ts` — the shared fetch wrapper (`request<T>`) returns `response as unknown as T` for raw-response mode (`:413`), `(await response.text()) as unknown as T` for SSE streams (`:489`), `(await response.blob()) as unknown as T` for binary responses (`:492`), and — with no cast operator visible at all — the ordinary JSON path (`:495`, `return response.json();`) is implicitly widened from `Promise<any>` to the caller's declared `Promise<T>` by TypeScript's `any`-is-assignable-to-anything rule, which is the same escape hatch with even less visibility (no `as` to grep for). **Every API call in the entire portal trusts the backend's JSON body to exactly match its declared TypeScript response type, with zero runtime schema validation anywhere in the client** (no zod/io-ts/runtime parsing found anywhere under `src/lib/api/`). This isn't a single "known-broken contract" the way the Issues `ignored` gap (section 5) is — it's the app-wide absence of a runtime check backing every declared response type, so if the backend ever ships a shape that drifts from a hand-maintained `resources.ts` interface, the failure mode is a downstream `undefined`/`TypeError` deep in a component rather than a clear "API contract changed" error at the fetch boundary.

## 10. Forms/input-validation sweep — no new bugs found; both real forms validate correctly, one "form" isn't actually a form

Found every `onSubmit`/`handleSubmit` site in the portal (`grep -rln "onSubmit\|handleSubmit" src --include="*.tsx"`, excluding tests): `signals/automations-panel.tsx`, `signals/signals-client.tsx`, `agents/agents-client.tsx`, `lab/traces-session-lens.tsx`, `lab/settings/settings-workspace-view.tsx`, `lab/agent/agent-composer.tsx`, `components/marketing/contact-form.tsx`. Checked the three most plausible candidates for a validation gap:

- **`components/marketing/contact-form.tsx`**: has `type="email"` + `required` HTML attributes but zero JS-side validation and zero `try`/`catch` in its `onSubmit`. Investigated why this might be a gap — **it isn't**: the handler (`:11-27`) never calls the backend at all; it builds a `mailto:` URL from the form fields and does `window.location.href = "mailto:..."`. There's no network request to fail, so "no validation before submit" and "no error handling" are both moot for this one — it hands off entirely to the user's mail client.
- **`signals/automations-panel.tsx`** (`submit`, `:199-236`): genuinely validates before calling the backend — `name.trim()` required (`:202`), numeric `threshold` checked with `Number(threshold)` + a dedicated error message (`:210`), and the advanced-mode JSON config is validated with a `JSON.parse` inside its own `try`/`catch` that sets a specific "Advanced action config must be valid JSON" error (`:216-220`) *before* the network call. The outer `try`/`catch` around the actual `automationsApi.create` call (`:226-236`) surfaces `err.message` — and since `ApiError` messages are already passed through `toUserFacingError` server-response-detail-first in `core.ts` (section 9), a real 4xx validation failure from the backend does reach the user as that field's actual detail message, not a generic string. No gap.
- **`lab/settings/settings-workspace-view.tsx`** (workspace rename, `:70-89`): validates `next.trim()` is non-empty and different from the current name before calling `onRename` (`:73-75`), wraps the call in `try`/`catch`/`finally` (`:80-88`), and defers the actual user-facing error surfacing to the parent via toast (comment: `/* parent toasts failure */`) — a legitimate delegation pattern, not a swallowed error, confirmed the parent (`SettingsWorkspaceView`'s caller) does push a toast on `onRename` rejection.

No new form-validation bugs found this pass; the systemic issue that touches all of these is the same one from section 9 (no runtime response-shape validation), not missing pre-submit input validation.
