# F15 — Artifacts / Book / Ledger: un-stub eden's existing GA-default behavior record (Lemma parity)

**Status:** Fourth research pass, materially rescoped from the prior three. Ground truth per the product owner: Lemma (YC F25) ships a live feature called **Artifacts** — "a record of how yours is supposed to work from its prompts, traces, and the context only your team knows... As your agent changes, that record updates with it. Lemma uses it to decide what should surface as an issue, and every issue you validate or dismiss updates what it looks for next." Passes 1–3 escalated from "can't find it" to "confirmed real via Lemma's API docs" to "here is the engineering spec eden should build." **That last step was wrong.** This pass found that eden already built and shipped the equivalent — under the literal name "Artifacts" — as `src/eden/nudges/` (class `ArtifactAuthor`, class `ArtifactDemotionWorker`), plus a companion versioned prose record named the **Book** (`src/eden/kb/book/`) and a structured, cited, embedded, retrieval-grade version named the **Ledger** (`src/eden/kb/ledger/`). Both are gated by feature flags literally named `artifacts_v1` and `ledger_v1`, which default **on** for every org (`src/eden/preview/gates.py:11-12`, docstring: *"GA surfaces: missing org feature key means enabled"*). The gap is not a missing system — it's that the portal routes reserved for it (`/artifacts`, `/ledger`) are wired as dead stubs that redirect to `/improve?mode=queue` (`clients/portal/src/lib/stub-try-instead.ts:9,22`), and a handful of connective-tissue wiring pieces (team-uploaded context, a prompt-version-changed regen trigger, an MCP tool, `TriageAgent` reading the Ledger before its ReAct loop) were never finished. This doc now specifies **completing and surfacing** that system, not designing a new one.

## TL;DR

1. **Headline correction, this pass: the "concrete gap" in the prior version of this doc was mostly wrong.** eden already has a shipped, GA-default, end-to-end record: `nudges` (individual behavior-change patches with a `shadow → promoted → archived` lifecycle, authored by `ArtifactAuthor`, evidence-gated via `EvidenceGate`, auto-demoted from real production outcomes by `ArtifactDemotionWorker`), the **Book** (`BookGenerator`, four fixed markdown chapters: Recent failures / Proven fixes / Tool-MCP gotchas / Do-not-repeat, versioned, regenerated on issue-resolve), and the **Ledger** (`agent_ledgers` + `ledger_entries`: chaptered, weighted, cited, embedded entries with a working `diff_since_version()` query). All three are wired into a real, live REST API (`src/eden/api/routes/learn.py`) and, critically, **the Book/Ledger is injected directly into live production prompts** via `BookGatewayFilter` (`src/eden/llmops/filters/book.py:33-71`) — the record a human would browse and the context steering the agent's next completion are the same versioned artifact.
2. **UUID vs. VARCHAR conflict with `13-continuous-improvement-loop.md`, resolved: F13 is correct, this doc's prior draft was wrong.** F13 explicitly corrects a "prior pass" (this doc) that proposed `nl_signals.agent_id UUID`, and verifies against the live schema that `agent_id` is a free-form string column everywhere it appears — `agent_issues.agent_id` and `agent_stumbles.agent_id` are both `VARCHAR(256)` (`src/eden/db_migrations/versions/084_agent_issues.py:49,93`), and the Book/Ledger/nudges tables use `agent_id TEXT NOT NULL` (`092_market_ready_consolidated.py:146`, `100_artifacts_ledger.py:20,35`) — never `UUID`, and never FK'd to an agent-registry table (none exists). `org_id`, by contrast, **is** `UUID REFERENCES organizations(id)` in these same newer tables. This doc's data-model proposal below is corrected to match: `agent_id TEXT`/`VARCHAR`, never UUID.
3. **eden's own confirm/dismiss loop is stronger than the one this doc originally proposed, and doesn't wait on a human to click a button.** `ArtifactDemotionWorker.run_once()` (`src/eden/nudges/demotion_worker.py:11-89`) scans `nudge_outcomes` over a rolling 7-day window (≥10 applications, >50% real stumble rate from actual traced requests) and auto-archives regressed nudges, writing the "why" as a Ledger `do_not_repeat` entry. This is a materially better mechanism than the operator-click `operator_confirms`/`operator_dismisses` counters this doc previously proposed building from scratch — it's outcome-driven, already shipped, and doesn't inherit F13's `record_shadow_feedback`-has-zero-callers problem (that problem is real, but it's scoped to the `nl_signals` shadow-detector loop, not to Artifacts/Book/Ledger).
4. **Market corroboration (Lemma) is unchanged from the prior pass and still holds** — see "Market context" below.
5. **Verdict: UN-STUB, not build.** The real work is: (a) remove `/artifacts` and `/ledger` from the portal's dead-stub map and build the pages against APIs that already exist, (b) ship the Ledger's already-built `diff_since_version()` as a "what changed" view (best value/effort ratio available in this entire feature), (c) wire `TriageAgent` to read `LedgerGenerator.get_latest()` before its expensive 8-call ReAct evidence loop, (d) add the one genuinely-missing piece — team-uploaded `.txt`/`.md` context, Lemma's `uploaded_text_artifacts` analog, which does not exist anywhere in `kb/` today — and (e) wire the one missing regeneration trigger (prompt-version-changed). Total estimate is days, not the "1.5–2 weeks to build a new schema" the prior draft of this doc claimed.

### What this pass found: Lemma's own API docs

`docs.uselemma.ai`'s OpenAPI reference (via its `llms.txt` index) has a **dedicated `Artifacts` tag** with these operations, quoted directly from the spec:

- `POST /projects/{project_id}/artifacts/regenerate` — *"Starts the learn-agent workflow for a tenant-owned project and optional agent. Duplicate project+agent triggers within the dedupe window return the same workflow_id; clients should poll list_project_artifacts for a new latest_version or learn_agent_artifact version to observe completion."* Response: `{workflow_id, project_id, agent_name}`.
- `GET .../artifacts` (list learn-agent artifact versions) — *"Returns learn-agent KB version metadata for a project and agent, newest first... The response omits artifact content."* Each item: `{version, run_id, agent_name, created_at, updated_at}`.
- `GET .../artifacts/{version}` (get learn-agent artifact version) — returns the actual content.
- `POST /projects/{project_id}/artifacts` (upload project artifact) — *"Upload an agent-scoped .txt or .md file (text/plain or text/markdown)."* Params: `project_id`, optional `agent_name` ("Optional agent name to attach to this uploaded artifact"). Response includes `id, project_id, agent_name, filename, content_type, size_bytes, created_at`.
- `GET/DELETE` list/delete uploaded and generated artifacts; `List project artifacts` (both kinds together).

And, tying Artifacts directly to Issues — the exact link the product-owner-provided copy describes ("Lemma uses it to decide what should surface as an issue"):

- `GET /issues/{issue_id}/artifact-context` — *"Returns bounded learn-agent and uploaded text artifact context for validation and debugging."* Response schema: `available: {learn_agent_kb: bool, uploaded_text_artifacts: bool}`, `learn_agent_kb: {version, agent_name, knowledge_preview, mermaid_preview, knowledge_truncated, mermaid_truncated}`, `uploaded_text_artifacts: [{id, filename, content_type, size_bytes, content_preview, preview_truncated}]`, `caveats: []`.

This maps field-for-field onto the product owner's copy: **`learn_agent_kb`** (auto-synthesized from traces, versioned, `regenerate`-able, includes a **mermaid diagram** preview of the agent's behavior) is "how yours is supposed to work from its prompts, traces"; **`uploaded_text_artifacts`** (agent-scoped `.txt`/`.md` files a team uploads) is "the context only your team knows"; the `regenerate` endpoint's dedupe-and-poll semantics are "as your agent changes, that record updates with it"; and `get_issue_artifact_context` being the exact input an issue's validation/debugging pulls from is "Lemma uses it to decide what should surface as an issue." The docs reference does not expose an explicit endpoint proving the "every confirm/dismiss updates what it looks for next" half of the claim (the closest is `Set issue status` / `Flag or unflag issue` / `Start issue review` under the Issues tag, without visible artifact-side plumbing in the docs) — noted honestly as the one part of the product-owner copy not independently confirmed in public material, though nothing contradicts it either, and it is exactly the shape of loop Lemma's own blog post describes generically ("expanding evaluations: turning real-world failures into new metrics").

### Broader 2026 competitive landscape for "living spec" concepts

- **Braintrust** — closest functional analog, already documented in F13 (production trace → dataset → eval → CI gate → production scoring → back into dataset). This pass adds: "Topics" auto-classifies every trace by intent/recurring issue; "Loop" (AI assistant) turns natural-language investigation into new evaluators from trace data; traces convert to eval datasets "in one click" ([braintrust.dev/articles/agent-observability-complete-guide-2026](https://www.braintrust.dev/articles/agent-observability-complete-guide-2026)). No single named "Artifact" object — the living spec is implicit across the dataset/eval/prompt-version graph, not a persisted per-agent record you can view.
- **Galileo** (acquired by Cisco, deal announced Apr 9 2026, closed May 22 2026) — markets a "living asset" framing: SME annotations "create a living asset that continuously grounds your AI systems," and "today's evals are tomorrow's guardrails" ([galileo.ai](https://galileo.ai/), [Cisco Blogs](https://blogs.cisco.com/news/cisco-announces-the-intent-to-acquire-galileo)). Philosophically the closest match to "record that updates as the agent changes"; no named per-agent record object found.
- **Maxim AI** — issues found in production observability get reproduced in simulation, fixed in "Playground++," verified via eval, "without leaving the platform," with the same evaluators running pre-release and in production ([getmaxim.ai/articles/top-5-ai-agent-monitoring-platforms-in-2026](https://www.getmaxim.ai/articles/top-5-ai-agent-monitoring-platforms-in-2026/)). Same round-trip shape, no persistent named record.
- **LangSmith / Arize** — per F13, ecosystem-coupled and observability-first respectively; neither markets a persistent-behavior-record object.
- **Academic grounding for what "Artifacts" is functionally doing** — two 2026 papers give real vocabulary:
  - **Agent Behavioral Contracts (ABC)** — Bhardwaj, [arXiv:2602.22302](https://arxiv.org/pdf/2602.22302) (Feb 2026). Argues agents run on prompts with "no formal behavioral specification," and formalizes a contract `C = (P, I, G, R)` — Preconditions, Invariants, Governance, Recovery — as runtime-enforceable. Implemented as `AgentAssert`, benchmarked on `AgentContract-Bench` (200 scenarios, 7 models, 1,980 sessions): contracted agents catch 5.2–6.8 soft violations per session that uncontracted baselines miss entirely (p < 0.0001), at <10ms overhead per action. This is the "hard, formally-verified contract" end of the spectrum — a legal document, not a descriptive record.
  - **Willful Disobedience / AgentPex** — Sharma, Barke, Zorn (Microsoft Research), [arXiv:2603.23806](https://arxiv.org/abs/2603.23806v1), ACM CAIS 2026. Extracts checkable behavioral rules directly from an agent's own system prompt + tool schemas, then evaluates traces for compliance. Key finding: **83% of "perfect reward" Claude traces on τ2-bench still had procedural violations** invisible to outcome-only scoring. This is functionally very close to what an eden Artifact's synthesized summary should be checked against — a rule-set derived from the live prompt, evaluated against traces, distinct from the raw prompt text.

  Both validate Lemma's commercial thesis: **prompts alone are not a checkable spec — you need a derived, versioned, trace-grounded record to check against.** eden's already-shipped Book/Ledger (`agent_books.content_md` / `ledger_entries.text`, below) is the descriptive/soft version of this; AgentPex-style rule extraction is a natural, harder-edged follow-on once the descriptive record exists — explicitly scoped as future work, not v1 (see Verdict).

## What eden already has — a shipped, GA-default Artifacts/Book/Ledger system

Unlike passes 1–3 assumed, this is not a set of disconnected fragments to be wired into a new record. It is one coherent, already-live system, three layers deep, all keyed `(org_id, agent_id)`:

1. **Artifacts (`nudges`) — individual, lifecycle-managed behavior-change patches.** `nudges` table (`092_market_ready_consolidated.py:143-157`: `id, org_id UUID, agent_id TEXT, name, trigger JSONB, action_type, content, mode CHECK IN ('shadow','promoted','archived'), source_issue_id, evidence JSONB, created_at, promoted_at, archived_at`). Authored by `ArtifactAuthor` (`src/eden/nudges/author.py:11`) via three real entry points: `from_issue()` (`:42-77`, template-first, no LLM), `from_loop_report()` (`:14-40`), and `from_nl()` (`:79-139`, budget-gated at `EvolutionSpendBudget.may_spend(0.01)`, only escalates to an LLM call for descriptions over 200 chars — a genuinely cost-conscious authoring pattern). New nudges land `mode='shadow'` and are queued into `EvidenceGate` (`promotion/evidence_gate.py`) for evidence-gated promotion. Applied live to gateway requests via `apply_nudge_to_prompt` (`nudges/engine.py:191-226`: `request.prompt = f"{prompt}\n\n<!-- eden-nudge:{nudge.id} -->\n{nudge.content}"`). Auto-demoted by `ArtifactDemotionWorker.run_once()` (`nudges/demotion_worker.py:11-89`) — scans `nudge_outcomes` over a rolling 7-day window, archives any promoted nudge with ≥10 applications and a >50% real stumble rate, and writes the reason as a Ledger `do_not_repeat` entry. This is the Lemma-`Issues`-adjacent unit: a feed of small, individually-actionable patches with a lifecycle, not a single prose document.
2. **The Book — versioned prose summary.** `BookGenerator._synthesize()` (`src/eden/kb/book/generator.py:91-136`) renders four fixed markdown chapters every regeneration: *Recent failures* (last 10 resolved `agent_issues`), *Proven fixes* (last 5 promoted nudges), *Tool/MCP gotchas* (currently a static stub string, `_DEFAULT_CHAPTERS:11-22` — not yet populated from real data), and *Do-not-repeat* (archived nudges + regressions). Each `generate()` call increments `agent_books.version` (`MAX(version)+1`, `:44-53`) and persists `content_md` + `token_count`. `get_latest(org_id, agent_id)` (`:138-158`) is exactly the "current understanding of agent X" query. This is closer to a structured changelog than a free-form essay — good for scanability, thinner than Lemma's `knowledge_preview` sounds.
3. **The Ledger — structured, weighted, cited, embedded entries (the retrieval-grade version).** `agent_ledgers` + `ledger_entries` (`100_artifacts_ledger.py:18-49`: each entry has a `chapter` (`recent_failures` | `do_not_repeat`, etc.), `text`, `citations` JSONB (e.g. `["artifact:{nudge_id}"]`, populated in `upsert_from_issue()`, `kb/ledger/generator.py:60-68`), a `weight` (do-not-repeat entries get `10.0` vs. default `1.0`, `:98`), a `version`, and an `embedding` used by `LedgerRetriever` for semantic packing into the live prompt. `diff_since_version()` (`:190-214`, `SELECT ... WHERE version > since_version ORDER BY created_at ASC`) is an **already-built version-diff query**, routed at `GET /agents/{agent_id}/ledger/diff` (`api/routes/learn.py:538-551`) — unused by any portal page.
4. **The record is injected into live production traffic, not just displayed — the single strongest argument this feature is genuinely useful, not bookkeeping.** `BookGatewayFilter.apply()` (`src/eden/llmops/filters/book.py:33-71`) prefixes the outbound prompt with the current Book excerpt (`<!-- eden-book:v{version} -->`) or, when `ledger_v1` is on, packs Ledger text via `LedgerRetriever().pack_sync()`. **The record a human browses in the portal and the context steering the agent's next completion are the same versioned artifact.** Any redesign must preserve this property; a purely-descriptive summary field with no injection path would be a regression relative to what already ships.
5. **Both systems are GA-default-on, per-org, by feature flag.** `_GA_DEFAULT_ON = frozenset({"artifacts_v1", "ledger_v1"})` (`src/eden/preview/gates.py:12`), with `_org_flag()` docstring stating explicitly: *"GA keys (`artifacts_v1`, `ledger_v1`): missing → enabled"* (`:37-43`). This is not an experimental or opt-in feature.
6. **The issue-resolve → shadow Artifact → promotion → Ledger pipeline is fully wired today, not proposed.** `resolve_issue`'s flywheel side-effect (`agent_issues.py:207-223`) calls `KBFlywheelCoordinator.on_issue_resolved()` (`kb/flywheel/coordinator.py:24-43`), which — when `stumble_count >= 3` — calls `ArtifactAuthor().from_issue(org_id, issue)`. Once a nudge is promoted, `on_promotion()` (`:215-244`) writes a `do_not_repeat` Ledger entry ("Proven fix: ...") or, if `ledger_v1` is off, regenerates the whole Book. Note: this is the *same* flywheel coordinator that appears elsewhere in eden's issue-resolve path — there is only one regen-on-resolve mechanism here, not two.
7. **A full REST surface already exists** at `src/eden/api/routes/learn.py`: `GET/POST /orgs/{org_id}/artifacts`, `POST /artifacts/{id}/promote`, `POST /artifacts/{id}/archive`, `POST /artifacts/author` (NL authoring), `GET /artifacts/export` (YAML export) (`:385-492`); `GET /orgs/{org_id}/ledger`, `GET /agents/{agent_id}/ledger`, `GET /agents/{agent_id}/ledger/diff`, `POST /agents/{agent_id}/ledger/regenerate` (`:498-581`); `GET/POST /agents/{agent_id}/book`, `/book/regenerate` (`:255-279`); plus `GET /agents/{agent_id}/drift`, `/drift/report/latest`, `POST /drift/compute` (`:295-324`) — a PSI-based statistical behavioral-drift score with no analog anywhere in the prior draft of this doc.
8. **The portal has reserved routes, breadcrumb labels, and written page copy for `/artifacts` and `/ledger` — wired as dead stubs.** `clients/portal/src/lib/portal-routes.ts:22,24` and `breadcrumbs.ts:81,87` (`artifacts: { label: "Artifacts", category: "improve" }`, `ledger: { label: "Ledger", category: "improve" }`) register the routes; `page-descriptions.ts:32-35` already has product copy written (*"Soft-lands on Improve queue — versioned runtime fixes with evidence-gated promotion"* / *"...institutional memory and promotion history"*); but `stub-try-instead.ts:9,22` redirects both to `/improve?mode=queue`, and both are also listed in `STUB_PORTAL_PATH_PREFIXES` (`portal-routes.ts`). A test (`nav-registry-parity.test.ts`, per `stub-try-instead.ts`'s own comment) enforces that a route must be removed from the stub map before it can go live — someone scoped this feature's portal presence and never shipped the page.
9. **No MCP tool exists for any of this** — confirmed by grep of `src/eden/mcp_server/tools.py` for `nudge|ledger|book|artifact`: zero hits. `triage_issue`, `run_autofix`, `export_fixture`, `get_improvement_plan` etc. exist; nothing surfaces the Book/Ledger/Artifacts to an MCP client. This part of the prior draft's "no unified surface" claim is the one part that still holds.
10. **`TriageAgent` does not read the Ledger.** `TriageAgent._gather_evidence()` (`triage_agent.py:319-358`, `_MAX_REACT_CALLS = 8`, `:47`) re-derives context from raw stumbles on every single triage call via an 8-call ReAct-lite loop — it never calls `LedgerGenerator().get_latest(org_id, agent_id)`, which already returns `{ledger_id, version, entries: [{chapter, text, citations, weight}]}` (`kb/ledger/generator.py:101-142`) as a cheap first pass.
11. **No team-uploaded context exists anywhere in `kb/`.** Lemma's `uploaded_text_artifacts` (agent-scoped `.txt`/`.md` uploads a human feeds in) has no eden equivalent — confirmed absent from `ledger_entries`'/`agent_books`' schemas (no `filename`/`content_type`/uploaded-by-human column anywhere in migrations `092` or `100`). This is the one genuinely net-new piece of data model worth building — see below.
12. **No diagram rendering exists anywhere.** `grep -rl mermaid src/eden/ clients/portal/src/` returns zero files — no Mermaid dependency, no SVG-graph component. Lemma's own `mermaid_preview` is a preview string in an API response per this doc's market research; nothing in the evidence gathered shows Lemma's own web app rendering it either, so parity pressure to ship a diagram in v1 is weak.
13. **The prompt-version-changed regen trigger is the one real gap in the trigger set.** issue-resolved (point 6) and manual NL-authoring (point 1, `POST /artifacts/author`) are both wired and live. Nothing today regenerates the Book/Ledger/Artifacts when `PromptService.create_version()` fires (`prompt_versioning.py:223`) — the same hook F13's P1 proposes for shadow-detector re-scout, unwired here for a different purpose.
14. **`nl_signals`/`record_shadow_feedback` remain the real, separately-scoped F13 gap** and are not part of this system. F13 found the shadow-detector confirm/dismiss loop fully built but disconnected (`record_shadow_feedback` has zero callers) and `nl_signals` has no `agent_id` column. Both matter for F13's shadow-detector promote/delete job; neither blocks Artifacts/Book/Ledger, which use `nudge_outcomes`-driven auto-demotion instead (point 4 in "What eden already has," above referencing `ArtifactDemotionWorker`).

## The concrete gap

Given the above, what's actually missing is small and precisely scoped:

- **The portal doesn't surface any of it.** `/artifacts` and `/ledger` are dead stub routes with product copy already written and no page built. This is the largest, highest-leverage gap — a human today hits a dead end trying to see "what has this agent learned."
- **The Ledger's diff view is built but unrendered.** `diff_since_version()` and its route exist; no UI calls it.
- **`TriageAgent` re-derives context from scratch every call** instead of reading the already-available `LedgerGenerator.get_latest()` first.
- **No team-uploaded context.** The one piece of Lemma's Artifacts with no eden equivalent at all.
- **No prompt-version-changed regen trigger.**
- **No MCP tool** surfaces Book/Ledger/Artifacts to MCP clients (e.g. Claude Code, Claude Desktop) the way `triage_issue`/`run_autofix` do for issues.
- **No diagram rendering** — real gap, but low-priority; defer explicitly rather than pricing it into a portal-tab estimate.

## User Experience & Value

### Who the user is, and what they're actually looking at

Not one artifact — three layers, all real, all per-`(org_id, agent_id)`:

- **Artifacts (`nudges`)** — a list of small, individually-actionable behavior patches, each tagged `shadow`/`promoted`/`archived`. The Lemma-`Issues`-adjacent unit: "what changed."
- **The Book** — four-chapter versioned prose snapshot. The Lemma-`learn_agent_kb`-adjacent unit: "current state," read as a structured changelog rather than free-form prose.
- **The Ledger** — the same idea as the Book, but structured, weighted, cited, and embedded for retrieval, with a working version-diff query.

eden's own product copy already conflates these into one "Artifacts" idea; the underlying system keeps them separate, and a portal design should probably keep that separation too (a "what changed" feed of nudges, plus a "current state" Book/Ledger view) rather than force them into a single object.

### Three distinct consumers, three distinct value propositions

1. **The live agent itself, at request time — the most important and most overlooked consumer.** `BookGatewayFilter` injects the current Book/Ledger directly into every outbound prompt (`llmops/filters/book.py:33-71`). The record a human reads and the context steering the agent's next completion are the same versioned object. A portal page should be able to say, truthfully, "version 7 of this Book is live in production right now" — not "here is a summary someone generated." This already works today, GA-default-on. No redesign should give it up.
2. **An on-call/triage engineer, mid-incident.** `TriageAgent._gather_evidence()` re-derives context from raw stumbles on every triage call via an 8-call ReAct-lite loop (`triage_agent.py:319-358`, `_MAX_REACT_CALLS = 8`). Wiring one cheap call to `LedgerGenerator().get_latest(org_id, agent_id)` as a first pass before that loop is the single highest-value, lowest-effort UX win available in this whole feature — speed-to-context during an incident, and it's a one-call fetch away today, not a schema change.
3. **A human browsing the portal to understand "what has this agent learned."** This is the smallest-leverage of the three audiences — a human reading a summary is strictly less valuable than the same summary steering live behavior (persona 1) or accelerating triage (persona 2) — but it's the one that's completely broken today: `/artifacts` and `/ledger` both redirect to `/improve?mode=queue` with no real page behind them, even though the API, the product copy, and the breadcrumb labels all already exist. **This is the actual, single largest UX gap in eden's Artifacts story: not a missing capability, a missing page against APIs that already work.**

### What the usage flow looks like today vs. after un-stubbing

**Today:** an agent's Book/Ledger is silently built and injected into production traffic on every request once `stumble_count >= 3` on a resolved issue triggers `ArtifactAuthor.from_issue` → evidence-gated promotion → Ledger/Book update. No operator ever sees this happen unless they query the API directly or read raw `nudges`/`agent_books` rows. Clicking "Artifacts" or "Ledger" in the portal nav silently redirects to the Improve queue, which shows something adjacent but not the same view. There's no way to see "what changed since I last looked," even though the query for it exists and is routed. `TriageAgent` never reads any of this, so triage pays a repeated, expensive ReAct-evidence cost per call.

**After the un-stub work below:** an operator can browse `/artifacts` for a lifecycle feed of nudges and `/ledger` for the current Book/Ledger plus a diff since last-viewed version; a triage engineer's investigations get materially cheaper and faster because `TriageAgent` reads the Ledger first; and a team can hand-feed org-specific context ("our refund policy requires X") the way Lemma's customers can today and eden's customers cannot.

### Concrete usability/adoption gaps

1. **The stub redirect is worse than a 404 for trust.** `/artifacts` silently lands on `/improve?mode=queue`, a page about something adjacent but different (the promotion queue, not the record itself). A user who doesn't already know the internal architecture has no way to tell "this doesn't exist" from "this is what Artifacts looks like" — actively misleading, not just incomplete.
2. **No citations rendered anywhere yet.** `ledger_entries.citations`/`source_ids` already exist and are populated (e.g. `["artifact:{nudge_id}"]`), but nothing in the API responses or a hypothetical UI has been asked to render them as clickable links back to the source issue/nudge. Without that, even a shipped portal page risks reading as "an assertion" rather than "a claim with receipts" — the exact failure mode that makes this look like internal bookkeeping instead of a trustworthy record.
3. **No visibility into *why* a nudge was auto-demoted.** `ArtifactDemotionWorker` computes a real stumble-rate number over a real 7-day window before archiving something — that number should be a first-class, surfaced fact ("archived: 62% stumble rate over 10+ applications, last 7 days"), not buried inside a Ledger paragraph.
4. **No MCP tool.** An agent-building user working from Claude Code/Claude Desktop via eden's MCP server has `triage_issue` and `run_autofix` but no way to ask "what has this agent learned" without leaving the assistant and going to the (currently broken) portal page.
5. **No team-authored input.** Unlike Lemma, there's no way today for a human to hand-feed org-specific context into what gets synthesized — the one real net-new capability worth building (below).

## What's still genuinely missing — data model additions

Everything else needed already exists as schema (`nudges`, `agent_ledgers`, `ledger_entries`, `agent_books`) and API (`api/routes/learn.py`). The one genuinely net-new table is team-uploaded context, Lemma's `uploaded_text_artifacts` analog. Types below match the convention actually used by the tables this needs to plug into (`nudges`, `agent_ledgers`, `ledger_entries`, migrations `092`/`100`): **`org_id UUID REFERENCES organizations(id)`, `agent_id TEXT`** — not `VARCHAR(128)`, and never `UUID` for `agent_id` (see TL;DR point 2 / the F13 correction).

```sql
CREATE TABLE agent_artifact_context (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id       UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
    agent_id     TEXT NOT NULL,
    filename     VARCHAR(256),
    content_type VARCHAR(32) NOT NULL DEFAULT 'text/markdown',
    content      TEXT NOT NULL,
    created_by   VARCHAR(128) NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_agent_artifact_context_agent ON agent_artifact_context (org_id, agent_id, created_at DESC);
```

Fold this into the existing pipelines rather than building a parallel system: `BookGenerator._synthesize()` and `LedgerGenerator`'s issue/promotion upserts should read `agent_artifact_context` rows for the agent and include them in what gets synthesized/injected; `BookGatewayFilter`'s injection path is unaffected (context flows in upstream of it, not as a separate injection point).

### API surface — one new endpoint, the rest already exist

- `POST /orgs/{org_id}/agents/{agent_id}/artifacts/context` — new; upload team `.txt`/`.md` context (mirrors Lemma's `upload-project-artifact`). Follows the existing envelope helpers already used in `learn.py`.
- Everything else a portal page needs already exists and is live: `GET/POST /orgs/{org_id}/artifacts`, `POST /artifacts/{id}/promote`, `POST /artifacts/{id}/archive`, `POST /artifacts/author`, `GET /artifacts/export`, `GET /orgs/{org_id}/ledger`, `GET /agents/{agent_id}/ledger`, `GET /agents/{agent_id}/ledger/diff`, `GET/POST /agents/{agent_id}/book`, `GET /agents/{agent_id}/drift` (all `api/routes/learn.py`).
- MCP tool `get_agent_artifact(org_id, agent_id)` — new; alongside `triage_issue`/`run_autofix` in `mcp_server/tools.py`; should call the same `LedgerGenerator.get_latest()` / `BookGenerator.get_latest()` the portal page uses.

### Portal UI — un-stub, don't invent a new tab

1. Remove `/artifacts` and `/ledger` from `clients/portal/src/lib/stub-try-instead.ts:9,22` and from `STUB_PORTAL_PATH_PREFIXES` (`portal-routes.ts`) — `nav-registry-parity.test.ts` will enforce that a real page exists once these are removed.

**Total estimate (Phases 1–6):** ~5–7 days — a wiring and frontend effort against a system that already exists, not the "1.5–2 weeks to build a new schema" the prior draft of this doc estimated.

## Verdict: UN-STUB / WIRE, not RESCOPE

- **The core idea is not just corroborated, it's already shipped.** eden independently built and named "Artifacts" (`nudges` + `ArtifactAuthor`/`ArtifactDemotionWorker`), plus a Book and Ledger, GA-default-on, before this review pass started looking. The market corroboration from Lemma (`docs.uselemma.ai`'s `Artifacts` API tag) is real and still useful context, but it is confirming a feature eden already has, not a feature eden needs to build.
- **The actual gap is UX and connective wiring, not schema design.** Un-stub two dead portal routes against APIs that already exist; ship an already-built diff query as a UI; make `TriageAgent` read the Ledger it already has a getter for; add the one genuinely-missing input (team-uploaded context); wire one missing regen trigger (prompt-version-changed); add one MCP tool. None of this requires a new `agent_artifacts` table, a new confidence-scoring mechanism, or a new confirm/dismiss surface — `ArtifactDemotionWorker`'s outcome-driven auto-demotion already does that job, and does it better (production-outcome-driven, not click-driven) than the operator-click counters this doc previously proposed building.
- **Stay out of formal contract enforcement for v1**, same conclusion as the prior pass, for the same reason: the ABC/AgentPex academic pattern (hard, runtime-verified preconditions/invariants) is a materially larger, separately-scoped effort, and isn't what Lemma ships either.
