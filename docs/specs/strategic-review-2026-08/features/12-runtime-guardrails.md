# F12 — Runtime Guardrails / Pre-Response Intervention

## Verdict: RESCOPE (KEEP the correction, but the "real gap" is wider than "just add an SDK helper")

The task premise ("eden is purely post-hoc, no inline intervention path") is
confirmed **false** — eden has a mature, fail-closed, synchronous guardrails
engine. That correction from the prior pass holds and is the single most
important fact in this file. What changed on this deeper pass: (1) the
detectors behind that engine are v0 **heuristics** (regex / trigram overlap),
not learned classifiers, which is a real quality gap versus the 2026
competitive set, not just an adoption gap; and (2) there is a **second,
more urgent problem** than "no SDK auto-invoke" — a live, already-shipped,
default-on code path silently swaps the content-safety engine out for an
unrelated trajectory-metrics engine whenever a caller passes a `trace_id`,
which is the normal case for any properly-instrumented caller; and (3) the
"promote an eval finding into an enforced guardrail" loop the prior pass
described as a single mechanism is actually **two different classes named
`EvalToGuardrailLink`** in two different modules, with incompatible
enforcement semantics — the one reachable through the documented endpoint
doesn't enforce anything, and the one that does enforce has no documented
endpoint, no way to undo it, and no UI anywhere. All three are corrections
to how this subsystem actually behaves, not just gaps in how much of it is
used.

## What already exists

- `InterventionEngine.evaluate_and_act` — `src/eden/guardrails/intervention.py:440` (`class InterventionEngine` starts `:399`, docstring runs to `:436`). Fetches every **active** org policy of type `prompt_injection`, `pii_redaction`, `hallucination`, `content_policy`, evaluates each against `text`/`context`, and returns the most-restrictive verdict (`allow`/`warn`/`redact`/`escalate`/`block`) plus `edited_text`.
- **Fail-closed, verified by direct read of the branches:**
  - Empty policy fetch failure → `verdict: "block", live: false, reason: "policy_fetch_failed"` (`intervention.py:490-504`).
  - Zero active policies → `verdict: "block", live: false, reason: "no_active_policies"` (`intervention.py:505-517`).
  - Only `judge_link` (declared-but-not-enforced) policies present → `verdict: "block", live: false, reason: "judge_link_not_enforced"` (`intervention.py:519-548`).
  - i.e. an org that hasn't configured anything gets `block`, not `allow` — the safe default is denial, confirmed by reading the code, not just the docstring.
- Direction-scoped policies (`input`/`output`/`both`, `policy.py:465-483` per prior pass — not independently re-walked this pass, low risk) so a `hallucination` policy scoped to `direction="output"` is skipped on `direction="input"` calls.
- Detector implementations (all in `src/eden/guardrails/detectors.py`), read in full this pass:
  - `PromptInjectionDetector.scan` (`detectors.py:143-229`) — **regex pattern list**, not an ML classifier: jailbreak phrasing ("pretend/act/behave as a jailbroken/unfiltered AI", `:80-86`), fake system-prompt injection (`"system prompt:"`, `"new instructions:"`, `:90-101`), and prompt-exfiltration asks ("reveal/dump/leak your system prompt", `:102-107`). A single regex hit is enough to flag (`_INJECTION_MIN_HITS = 1`, `:111-115`) — the module comment itself notes "a future SLM judge would lower this to e.g. 0.05 and require a confidence score," i.e. the team already knows this is a placeholder.
  - `PIIFirewall.redact` (`detectors.py:235-`) reuses `DEFAULT_PII_PATTERNS` from `src/eden/services/governance_intel/_common.py:118-138` — concrete regex coverage: SSN, credit card (Visa/MC/Amex/Discover), API keys (`sk_`/`pk_`/`api_key=`), RSA/EC private key blocks, AWS access keys, email. No phone number, no address, no name-entity (NER) coverage — regex-only, no NLP/NER model.
  - `HallucinationBlocker.check` (`detectors.py:352-`) — explicitly documented as "v0 ships two deterministic heuristics... The v1.4 SLM judge will replace this with a learned classifier behind the same surface" (`detectors.py:354-369`). The two heuristics: refusal-phrase substring match (`REFUSAL_PHRASES`, `detectors.py:119-131`), and raw **trigram (3-char n-gram) overlap** between candidate and context — `overlap_ratio < 0.2` → treated as ungrounded/blocked. This is materially weaker than AWS Bedrock's semantic contextual-grounding check or Automated Reasoning checks (below).
  - `LLMFirewall.firewall` (`detectors.py:491-`) is a **pre-call** composite of `PromptInjectionDetector` + `PIIFirewall` only — it does not touch hallucination or content policy, and it does not validate tool/function calls in any way.
  - `ContentPolicyEnforcer.enforce` (`policy.py:342-`) is an **org-admin-authored keyword/regex blocklist** (`spec.blocklist`, entries optionally prefixed `re:` for regex) — there is no trained toxicity/hate-speech classifier anywhere in `src/eden/guardrails/`. An org gets toxicity coverage only if it hand-writes a blocklist.
  - **No tool-call / function-call schema validation or action-boundary enforcement anywhere in the guardrails module** (confirmed by grep: no `tool_call`/`function_call` reference in `detectors.py` or `policy.py`).
- **`EvalToGuardrailLink` — correction to a claim in the prior pass: this name refers to two different, non-interoperating classes, not one.** `eden.guardrails.intervention.EvalToGuardrailLink` (`intervention.py:789-957`, class starts `:789`, not `:788` as an earlier pass cited) has `.promote()` (`:812-903`) and `.demote()` (`:905-957`); `.promote()` writes a `type="judge_link"` row plus a link row and is reachable via `POST /guardrails/promote-judge`. But it does **not** "promote into a live enforced policy" — `InterventionEngine.evaluate_and_act`'s `_enforced_types` (`intervention.py:521-528`) explicitly excludes `judge_link`, and the code comment at `:519-520` says so directly ("judge_link policies are declared but not evaluated here — do not advertise live enforcement solely because they exist"). `.promote()` also never calls the live gateway filter's `load_policies`. A **second, separate** class with the identical name, `eden.evaluation.eval_intel.integration.EvalToGuardrailLink` (`integration.py:69-256`), is the one that actually enforces — see "The real gap," part 5, below for the full trace and why this matters more than a naming collision.
- `InterventionLog.query` (`intervention.py:973`) and `GuardrailMetrics.dashboard` (`intervention.py:1014`) for observability on the guardrail layer itself.
- Full REST surface at `src/eden/api/routes/intelligence_guardrails.py`: `POST /policies`, `POST /evaluate`, `POST /injection/scan`, `POST /pii/redact`, `POST /hallucination/check`, `POST /content/enforce`, `POST /promote-judge`, `POST /firewall`, `GET /log`, `GET /metrics`, `GET /scan-history`.

## The real gap

### 1. Confirmed: zero SDK auto-invoke path (the adoption gap)
`evaluate_and_act(` has exactly two occurrences repo-wide: its own definition (`intervention.py:440`) and its single production caller, `POST /guardrails/evaluate` at `intelligence_guardrails.py:148`. A repo-wide grep for `"guardrail"` (case-insensitive) across `sdk/python/` and `sdk/ts-ai/` returns **zero matches** — confirmed directly this pass, not inferred. Nothing in either SDK wraps a completion call with a guardrail check; a customer must know to call `POST /guardrails/evaluate` themselves before showing output to their end user. Same integration shape as Lakera Guard's raw API — Lakera's differentiator versus eden isn't detection depth so much as a documented single-endpoint contract customers actually reach for.

### 2. New this pass — more serious: a default-on hot path silently bypasses the content-safety engine
`install_cat15_trajectory_replaces_intervention()` (`src/eden/observability/trace_quality/wiring.py:279-364`) **monkey-patches `InterventionEngine.evaluate_and_act` at the class level**, replacing it with a wrapper (`_wrapped`, `wiring.py:313-355`) that:
- Falls through to the *original* `evaluate_and_act` (the detectors described above) only when the caller passes **no** `trace_id` (`wiring.py:325-333`).
- Otherwise routes to `evaluate_trajectory_step` (`src/eden/observability/trace_quality/hooks.py:885-980`), which runs the **8 hot-path checks** (`hooks.py:269-278`): `_cost_guard`, `_token_guard`, `_loop_guard`, `_tool_dedup`, `_retry_storm`, `_schema_validator`, `_latency_guard`, `_finish_reason`. Read every one of these (`hooks.py:96-248`) — **none of them inspect `text` or `context` for PII, prompt injection, or hallucination.** They operate purely on numeric/metadata fields (`cost_usd`, `usage_total_tokens`, `loop_verdict`, `tool_repeat_count`, `recent_failure_count`, `latency_z`, `finish_reason`) that the `_wrapped` shim doesn't even populate from `text`/`context` (`wiring.py:335-340` builds `event` from only `text`, `context`, and two hardcoded placeholder loop fields).
- This is wired at API-process startup, unconditionally, via `install_all()` → `install_cat15_trajectory_replaces_intervention()` (`wiring.py:369-379`), called from `src/eden/api/app.py:814` on every pod boot. Both governing flags default **on**: `Settings.trace_quality_enabled: bool = True` and `Settings.trace_quality_hot_path_enabled: bool = True` (`src/eden/config.py:937,942`).
- Net effect: `POST /guardrails/evaluate` (`intelligence_guardrails.py:130-149`) accepts `trace_id` as an **optional query parameter**. If a customer passes it — the natural thing to do for any call made inside an instrumented trace — the PII/injection/hallucination/content-policy detectors described above **do not run at all**; the response verdict instead reflects unrelated cost/loop/latency heuristics. This is not "unfinished work behind a flag defaulting off," as the prior pass characterized it — it is a **shipped, tested** (`tests/e2e/test_trace_quality_e2e.py`, `tests/api/test_hot_path_p99_regression.py`, `tests/api/test_trace_quality_kill_switch.py`, `tests/experiments/test_enh_hot_path_check_order.py`), default-on behavior that quietly changes what "guardrails" means depending on one optional query param. Whether this is an intentional product pivot (trajectory-safety superseding content-safety at the same call site) or an unreviewed collision between two teams' work on the same class method is unclear from the code alone — either way it belongs on the radar of whoever owns bug triage for this review, since it directly undercuts the "mature guardrails engine" framing above for the common case.
- **Also confirmed by reading `_wrapped` line-by-line (`wiring.py:315-360`), not just its docstring:** `edited_text` in the hot-path response is set to the raw input `text` verbatim (`wiring.py:353`) — no redaction pass ever touches it. If a customer's call contains a live SSN or API key and passes `trace_id`, the returned "guardrails" response hands that same unredacted string straight back, wrapped in a `verdict` field that reflects a cost/loop check, not a PII check. This is stronger than "detection is skipped" — the response shape (`edited_text`, `matched_policies: []`) is the *same envelope shape* the real PII-redaction path returns, so a caller trusting the contract (`edited_text` = safe-to-display string) gets no signal anything is different, unless it specifically inspects the new `"feature": "trajectory_guardrail"` marker (`wiring.py:349`) — see "Is there any monitoring" below for why nothing does.

### 4. Is there any monitoring that would catch a real PII/injection leak today? No — confirmed silent, not just "probably silent"

Checked, in order: the guardrail-specific log/metrics classes described in "What already exists" above, the DB write path feeding them, the trace-quality-side write path, and every alerting config in the repo (`helm/`, `deploy/`, `tinybird/`).

- `InterventionLog.query` and `GuardrailMetrics.dashboard` (`intervention.py:973`, `:1014`) — the *only* guardrail-specific observability that exists anywhere in the codebase — read exclusively from the `intervention_log` table. That table is written by exactly one function, `_log_intervention` → the `INSERT INTO intervention_log` block (`intervention.py:102-118`), called from exactly one place: `intervention.py:748`, inside the **original** `evaluate_and_act`. The hot-path `_wrapped` (`wiring.py:315-360`) returns its dict directly and **never calls this insert** — confirmed by reading the full function body, not inferring from its docstring.
- Instead, `evaluate_trajectory_step` (`hooks.py:885-980`) writes fire-and-forget to a *different* table, `trace_guardrail_actions`, via an async drain queue (`hooks.py:901-905`) — and even that table only ever records the 8 numeric/metadata verdicts (cost, loop, latency, etc.), because the hot-path checks never look at `text` content in the first place. There is no table anywhere that would show "a hot-path call happened and here's whether PII was in it," because the code that could answer that question never runs.
- **Net effect on the org's own dashboard:** `GuardrailMetrics.dashboard`'s `total_interventions` / `redactions` counters silently *exclude* every `trace_id`-bearing call — a busy org that routes 100% of its guardrail traffic through instrumented (i.e. `trace_id`-bearing) calls will show a guardrails dashboard with near-zero activity, indistinguishable from "we never see any risky input" versus "the detector never runs." This is the exact false-confidence failure mode the Recommendation section below already warns about for SDK auto-invoke — it turns out to already be live today for anyone reading the existing dashboard.
- **Alerting infrastructure:** a repo-wide, case-insensitive grep across `helm/`, `deploy/`, and `tinybird/` for `guardrail`, `intervention_log`, `pii`, `prompt_injection`, `trace_quality_hot_path`, and `trajectory_guardrail` returns **zero matches in every directory**. There is no dashboard panel, alert rule, or Tinybird pipe anywhere in the repo that references the guardrails subsystem at all, in either its content-safety or trajectory-metrics form.
- **The one partial signal that exists, and why it doesn't help:** the hot-path response body does self-report `"feature": "trajectory_guardrail"` (`wiring.py:349`) instead of the normal policy-verdict shape — so this is not literally invisible at the wire level to a sufficiently paranoid integrator diffing response shapes. But nothing in eden's own code, portal (grepped `clients/portal/src` for `trajectory_guardrail` — zero hits), dashboards, or alerting reads or surfaces that field. By any operational definition — log line, metric, alert, dashboard tile — this is a fully silent gap today.

### 5. New this pass — two classes named `EvalToGuardrailLink` make the eval-promotion loop non-functional end-to-end

The prior pass (and `KNOWN-SUBSYSTEMS.md`) describes a single "confirm a judge verdict → it becomes a live enforced guardrail" loop. That description conflates **two separate classes, in two separate modules, with incompatible enforcement semantics**, reached via two separate REST namespaces:

- **(a) `eden.guardrails.intervention.EvalToGuardrailLink`** (`intervention.py:789-957`) — the class the prior pass and "What already exists" above cite. `.promote()` (`:812-903`) creates a `judge_link` policy, reachable via `POST /orgs/{org_id}/intelligence/guardrails/promote-judge` (`intelligence_guardrails.py:188-196`). It is **toothless**: `judge_link` is hard-excluded from `_enforced_types` (`intervention.py:521-528`), so `evaluate_and_act` never evaluates a policy this method creates, and `.promote()` never calls the live gateway filter's `load_policies` (confirmed by grepping every caller of `load_policies` repo-wide). This class does have a working `.demote()` (`:905-957`) — but it has **no REST route anywhere** (checked all 12 routes in `intelligence_guardrails.py`); its only caller is the automatic hook `GuardrailHook.on_judge_below_floor` (`promotion_hooks.py:860-894`), never a human-triggerable action.
- **(b) `eden.evaluation.eval_intel.integration.EvalToGuardrailLink`** (`integration.py:69-256`) — a different class, not mentioned anywhere in the prior version of this doc or in `KNOWN-SUBSYSTEMS.md`'s `guardrails/` entry. `.promote_to_guardrail()` (`:79-207`) gates on real quality thresholds (≥100 judge samples in 30 days, FPR ≤5% — `integration.py:99-118`) and, when it fires, **does** hot-reload `eden.llmops.filters.guardrail.GuardrailGatewayFilter` (`integration.py:177-192`) — a pattern/keyword scan running at the LLM gateway (`llmops/filters/guardrail.py:38-69`), architecturally separate from `InterventionEngine` entirely. This is the class that actually enforces live traffic. It's reachable only via a different namespace, `POST /orgs/{org_id}/intelligence/eval/promote-to-guardrail` (`intelligence_eval.py:214-221`), plus a shadow variant `POST .../eval/promote-to-shadow-guardrail` (`wave6_online.py:617-624`). **This class has no `.demote()`/disable method anywhere** in `integration.py`, `intelligence_eval.py`, or `wave6_online.py` — once a judge is promoted through the path that actually does something, there is no code path, route, or UI to take it back short of hand-editing the gateway filter's in-memory policy dict.
- **Zero UI wiring for either path.** A repo-wide grep of `clients/portal/src` for `promote-judge`, `promote_to_guardrail`, `promote-to-guardrail`, `eval_to_guardrail`, `EvalToGuardrailLink`, and `judge_link` returns no hits. Both `promotion_hooks.py` triggers (`on_judge_threshold_breach`, `:801-858`; `on_judge_below_floor`, `:860-894`) are automatic, judge-reliability-driven hooks in their own docstrings, not the backing logic for a person clicking "confirm" or "dismiss" anywhere in the product.

Net: the "confirm a signal → it becomes an enforced guardrail" loop this subsystem is supposed to provide does not exist as a single, working path today. The class reachable through the documented promote endpoint doesn't enforce anything; the class that enforces has no documented endpoint, no demote path, and no doc coverage before this pass; and neither is wired to any UI action. This is the same "silent behavior mismatch" failure shape as the `trace_id` hot-path bypass (part 2 above), one layer up — in the promotion mechanism itself rather than in the evaluator.

### 6. New this pass — the guardrails policy list page has a frontend/backend contract mismatch and likely never renders real data

Traced the full chain from SQL to render for the portal's one live guardrails surface, `GET .../guardrails/policies` (the only network call the guardrails portal UI makes — see "What already exists" caller-audit context above):

## User Experience & Value

**Who is the user?** Two personas, neither of whom the product currently builds a working surface for. (1) A customer's **platform/backend engineer** integrating runtime protection into their own agent, who would call `POST /guardrails/evaluate` directly — there is no SDK wrapper, so this means hand-rolling an HTTP integration against a raw endpoint discovered via OpenAPI/source reading, not a documented product. (2) A customer's **safety/compliance lead** (or an eden-internal admin acting on their behalf) who wants to turn a judge's validated finding into an always-on policy — the promotion loop described in part 5 above. Today's portal instead serves a third, much lower-value persona: someone passively browsing a read-only list of policy config. Neither of the two personas who'd actually configure or act on this system has a UI.

**The promotion flow, walked end to end as it exists today:** a safety lead notices (via some out-of-product channel — there's no in-portal affordance for this) that a Cat-3 judge reliably flags a bad pattern, and wants it enforced automatically going forward. The path that's documented and named for this (`POST /guardrails/promote-judge` → `intervention.EvalToGuardrailLink.promote`) is a dead end: it writes a `judge_link` policy that `evaluate_and_act` is hard-coded to skip (part 5 above), so the org's dashboard will show the policy as present, `status='active'`, with no error — and it will never fire. The path that actually works (`POST /intelligence/eval/promote-to-guardrail` → `eval_intel.integration.EvalToGuardrailLink.promote_to_guardrail`) lives under a different, undocumented route namespace, has no portal affordance pointing to it, and — once used — has no way to undo: no demote/disable method exists anywhere for it. So the realistic journey today is: **a user who wants to promote a judge finding either uses the documented-sounding endpoint and silently gets nothing, or has to already know about a second, unlisted endpoint to get real enforcement — and if they do, they can never turn it back off without editing the gateway filter's in-memory state by hand.** Both paths require reading Python source to discover; neither is one click, and no click exists in the portal for either.

**Authoring a base policy (not eval-promoted, just a plain `pii_redaction`/`prompt_injection`/etc. policy) is equally source-only.** `POST /guardrails/policies` takes an untyped `spec` dict whose shape (e.g. `content_policy` needs `{"blocklist": [...]}`, `re:`-prefixed entries for regex) is documented nowhere but the detector code (`policy.py:342-354`). Creating a policy sets `status='active'` immediately (`policy.py:237-240`) — there is no preview/dry-run: the portal's one extra guardrails tab beyond "Policies," `GuardrailsTestView`, explicitly renders `EmptyState({title: "Dry-run not connected", ...})` (`guardrails-detail-view.tsx:129-154`), and the nav component hard-codes a single visible tab with the inline comment "Test dry-run is not a live surface" (`guardrails-chrome.tsx:15-19`).

**Once something is live, there's no way to see it worked.** `InterventionLog.query` and `GuardrailMetrics.dashboard` exist server-side (`GET /log`, `GET /metrics`) but nothing under `clients/portal/src/lab/guardrails/` renders either. Even if a user calls those endpoints directly, per the hot-path bypass (part 2 above) and the `judge_link_not_enforced` state (part 5), a normal-looking `verdict: allow` response gives no signal whether a real content-safety check ran, an unrelated cost/loop check ran instead, or a declared-but-unenforced policy was silently skipped — the one field that would disambiguate this (`"feature": "trajectory_guardrail"`) isn't surfaced anywhere in the product. And the one policy-list page that does exist likely renders nothing real for a populated org, per part 6 above — it currently "works" only because the test org has zero policies, so the envelope/enum mismatch never gets exercised.

**Why this would be valuable if it worked:** the underlying engine (fail-closed, direction-aware, with a real FPR/sample-gated promotion path in class (b)) is a genuine differentiator over "no inline intervention," and the promotion concept — validated judge finding becomes a live guardrail with one action — is exactly the kind of self-tightening loop competitors don't obviously have (closest analog: Bedrock's static policy config, no learned-from-your-own-judges loop). But right now that value is entirely theoretical: it exists as backend plumbing across two disconnected classes, reachable only by someone willing to read source and hit raw endpoints, with a documented-looking dead end, an undocumented working path with no undo, and a portal that can't display any of it correctly.

**Concrete fixes needed before this is usable by anyone but a source-reading engineer, in the order that unblocks the most:**
1. Collapse the two `EvalToGuardrailLink` classes into one — either make (a)'s `.promote()` call the same gateway-filter hot-reload (b) does, or delete (a) and repoint `POST /guardrails/promote-judge` at (b)'s logic. A promote endpoint that silently does nothing is the single worst state for a "confirm and enforce" action to be in.
2. Give the enforcing class a demote/disable route, symmetric with promote — today a noisy promoted guardrail can only be turned off by hand-editing the gateway filter's in-memory policy dict.
3. Fix the policy-list page's envelope unwrap and reconcile the frontend `kind` enum with the backend `type` enum (drop `toxicity`/`tool_allowlist`/`rate_limit`, which describe protections eden doesn't have) before adding any new portal surface on top of it.
4. Build a minimal confirm/dismiss UI on top of the consolidated promote/demote routes — the FPR/sample-gate evidence already computed in class (b) (`integration.py:99-118`) is enough to render as a card ("this judge would have blocked N% of traffic at threshold T, FPR F%") with real Promote/Dismiss buttons, which is the "one click → live, one click → gone" experience the current framing implies already exists.
5. Surface `GuardrailMetrics.dashboard`/`InterventionLog.query` in the portal, and expose the `feature`/`judge_link_not_enforced` state wherever a verdict is shown, so a user can tell "protected" from "silently not protected" without reading source.

### Is "hot path silently skips safety checks" a known anti-pattern? Yes, on two independent axes

**AI-guardrails-specific axis:** AWS Bedrock Guardrails' documented architecture evaluates *all* configured policies (content filters, PII, topic policies, contextual grounding) **in parallel, unconditionally, on every invocation** — the parallel design exists specifically so adding more checks doesn't force a latency-vs-coverage tradeoff (~30% overhead whether 3 PII types or the full enterprise suite are enabled). Its `ApplyGuardrail` API is likewise a decoupled, single-purpose evaluator: pass a payload, get a verdict, no branch that reroutes to an unrelated check set based on caller-supplied metadata. There is no code path in Bedrock's architecture — or in the general 2026 guardrails-architecture guidance surfaced this pass — where an optional request parameter causes PII/injection detection to be silently swapped for something else; the explicit design principle is that enforcement should be *structural* ("the block is structural, not instructional"), and the hot-path/cost tension competitors do wrestle with (LLM-judge latency is genuinely expensive — 5-11s per check cited for GPT-class judges) is solved by tiering *fast, lightweight, content-aware* checks against *heavier* ones, never by routing to checks that don't inspect content at all. Eden's `_wrapped` shim does exactly the thing this architecture pattern is designed to prevent: an `if trace_id: run unrelated checks` branch, not a fast content-aware pre-filter.

**General software-engineering axis, independent of the AI domain:** the mechanism itself — `intv.InterventionEngine.evaluate_and_act = _wrapped` (`wiring.py:363`), a class-level monkey-patch installed unconditionally at process boot — is a long-documented anti-pattern for exactly this failure mode. Shopify's engineering team's public account ("The Case Against Monkey Patching") describes a structurally identical incident: a monkey-patched Rails internal silently changed query-cache behavior with no exception thrown, went undiagnosed for weeks, and was only caught by accident. The general guidance from that and other 2026 sources is consistent: prefer dependency injection, subclassing, or an explicit adapter/wrapper over patching a class method in place, specifically because a patch that changes behavior *without raising* is next to impossible to catch through normal testing or error monitoring — which is exactly what part 4 above confirms happened here. Eden's case is worse on two counts a generic monkey-patching bug isn't: (1) the silently-changed behavior is a security control, not a caching layer, and (2) unlike the Shopify incident there is no "someone happened to notice" backstop at all — no dashboard, log, or alert makes the divergence visible (see "Is there any monitoring" above).

## Recommendation

Do **not** build a new guardrails engine from scratch — one exists and its core detection architecture (fail-closed, direction-aware) is sound. The eval-promotion loop, however, is **not** sound as shipped — see item 2. Six concrete next steps, in priority order:

1. **Resolve the hot-path collision first.** Before wiring an SDK auto-invoke helper on top of `evaluate_and_act`, determine whether `trace_quality_hot_path_enabled` silently disabling PII/injection/hallucination detection whenever `trace_id` is passed is intended behavior. If not intended, this should block any adoption push — auto-invoking a "guardrail" that's actually running cost/loop checks under the hood would be worse than the current opt-in-only status quo, because it creates false confidence. Flag to whoever owns bug triage in this review pass.
2. **Collapse the two `EvalToGuardrailLink` classes** (part 5 above) into one working promote/demote path, and give the enforcing class a demote/disable route (it currently has none). As shipped, the documented promote endpoint (`POST /guardrails/promote-judge`) is a dead end and the endpoint that actually enforces (`POST /intelligence/eval/promote-to-guardrail`) is undocumented and can't be undone — this needs a decision and a fix before the "eval-promotion loop" can be described as working at all, let alone adopted.
3. **Fix the guardrails policy list page's frontend/backend contract mismatch** (part 6 above): unwrap the API envelope in `portalApi.guardrailPolicies`, and reconcile the frontend `kind` filter enum with the backend `type` enum (the two currently share zero values, and two of the five filter chips describe protection categories eden doesn't have). This is the one portal surface that exists for this subsystem and it likely renders nothing real today.
4. **Close the adoption gap** identified in the prior pass: an opt-in SDK-level convenience (`sdk/python`, `sdk/ts-ai`) that wraps a completion call and auto-invokes `evaluate_and_act` on output before returning it to caller code, so guardrails becomes a config flag instead of a manual `POST /guardrails/evaluate` integration step. Concretely: a `guardrails=True` (or policy-id list) kwarg on the SDK's trace/completion wrapper that, post-response, calls the existing `/guardrails/evaluate` endpoint (or the in-process `InterventionEngine` directly if the SDK runs server-side) and raises/redacts based on the verdict before returning control to the caller — this is genuinely a thin wrapper given the engine underneath is already there.
5. **Upgrade detectors from v0 heuristics toward learned models** where the code already flags the intent to do so (hallucination "v1.4 SLM judge," injection "future SLM judge... confidence score") — this closes the detection-quality gap versus Lakera/Bedrock, independent of the SDK wiring work.
6. **Tool-call/action-boundary validation is the one category with no plan at all in the codebase** — worth scoping as new (not adoption) work, though note even the leading competitors treat this as immature in 2026, so it's not an urgent competitive gap, just a genuine capability hole.
