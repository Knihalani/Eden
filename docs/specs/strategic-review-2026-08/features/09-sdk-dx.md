## Industry context (2026)

- **OTel GenAI semantic conventions.** OTel's GenAI SIG (formed April 2024, under CNCF governance) defines a standard `gen_ai.*` attribute namespace: `gen_ai.request.model`, `gen_ai.usage.input_tokens`/`output_tokens`, `gen_ai.response.finish_reasons`, `gen_ai.operation.name` (required on every GenAI span), plus agent attributes (`gen_ai.agent.id`, `gen_ai.agent.name`, `gen_ai.agent.description`) and MCP tool-call attributes (`gen_ai.tool.name`, `mcp.method.name`, `mcp.session.id`). Adopted by Google Cloud, AWS, Azure, Datadog. Every doc in the spec's now-dedicated `open-telemetry/semantic-conventions-genai` repo is marked `Status: Development` — actively evolving but in production use. [Gen AI attribute registry](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/) · [semantic-conventions-genai repo](https://github.com/open-telemetry/semantic-conventions-genai) · [OTel blog: Inside the LLM Call](https://opentelemetry.io/blog/2026/genai-observability/) · [Greptime writeup](https://greptime.com/blogs/2026-05-09-opentelemetry-genai-semantic-conventions)

- **Four onboarding patterns competitors use, from lowest to highest friction:**
  1. **Proxy / zero-code** — Helicone: swap `base_url` (e.g. `https://oai.helicone.ai/v1`) and add one auth header; no SDK install, no wrapper. Now in maintenance mode after a March 2026 Mintlify acquisition, so this is a pattern to borrow, not a vendor to benchmark against. [Helicone GitHub](https://github.com/Helicone/helicone) · [Helicone base URL docs via LiteLLM](https://docs.litellm.ai/observability/helicone_integration)
  2. **Drop-in client wrapper** — LangSmith's `wrap_openai(openai.Client())` and Braintrust's `wrapOpenAI(new OpenAI())`/`initLogger()` both replace the client object in place; every call after that is traced with zero call-site changes, plus a `@traceable`/`wrapTraced` decorator for custom spans. Braintrust extends this to Anthropic, Gemini, Bedrock, LangChain, LangGraph, LlamaIndex, CrewAI "with no rewrites." [LangSmith README](https://github.com/langchain-ai/langsmith-sdk/blob/main/python/README.md) · [Braintrust OpenAI wrapper source](https://github.com/braintrustdata/braintrust-sdk/blob/main/js/src/wrappers/oai.ts) · [Braintrust logs guide](https://www.braintrust.dev/docs/guides/logs/write)
  3. **One-line global auto-instrument** — Traceloop/OpenLLMetry: `Traceloop.init()` patches 20+ providers/frameworks via OpenTelemetry with zero further code changes anywhere in the app (not just one client instance). Known failure mode: a single broken provider instrumentation can fail the entire `init()` call. [OpenLLMetry GitHub](https://github.com/traceloop/openllmetry) · [init() bug report](https://github.com/traceloop/openllmetry/issues/343)
  4. **OTel-native SDK** — Langfuse rewrote both SDKs onto OpenTelemetry (Python SDK v3, GA June 2025; JS rewritten to v4 in Aug 2025, then v5 in March 2026): `get_client()` / `@observe()` in Python, `observeOpenAI()` drop-in wrapper + `@langfuse/otel` span processor in JS. Because it's OTel-native, any third-party OTel-instrumented library (e.g. `opentelemetry-instrumentation-anthropic`) nests into the trace automatically with no Langfuse-specific glue. [Langfuse Python SDK v3 GA](https://langfuse.com/changelog/2025-06-05-python-sdk-v3-generally-available) · [Langfuse SDK overview](https://langfuse.com/docs/observability/sdk/overview) · [Langfuse JS SDK repo](https://github.com/langfuse/langfuse-js) · [observeOpenAI / Vercel AI SDK integration](https://langfuse.com/integrations/frameworks/vercel-ai-sdk)

  Two things every one of these has that eden's TS SDK currently lacks: a **single call that requires zero further per-client wiring**, and (for the OTel-native ones) attribute-level interop with any other OTel-GenAI-compliant instrumentation already running in the app.

This is a real, fixable DX gap between eden's own two forward SDKs, and puts TS's zero-argument path behind both Traceloop's and Langfuse's newer JS SDK on the same axis (Langfuse's `observeOpenAI()` is a single call per client, no manual `wrap*` selection required).

**No OTel GenAI semantic-convention support in either SDK.** `grep -rn "gen_ai\." sdk/ts-ai/src sdk/python/eden_sdk` returns **zero matches** in either tree (verified directly). Both SDKs ship eden's own bespoke event schema end to end. The OTLP bridge (`sdk/python/eden_sdk/otel.py`'s `configure_exporter`/`is_configured`, `sdk/ts-ai/src/otel.ts`'s equivalents) forwards generic OTLP spans to eden's ingest endpoint but neither reads nor writes `gen_ai.*` attributes — a span produced by another vendor's OTel-GenAI-compliant instrumentation carries no fields eden's UI understands, and eden's own OTLP export isn't self-describing as GenAI-standard to any OTel-native backend it might be piped to. ### Why TS lacks auto-instrumentation: mechanism, not intent

This is a real architectural gap, not a fundamental language limitation — traced to source on both sides.

**How Python's `install()` actually patches (13/13 frameworks, same pattern).** Every `instrumentations/*.py` module does direct, class-level attribute assignment on the already-imported library, guarded by a module-global idempotency flag: `openai.py:38` `install()` saves `_original_async_create = chat_completions.AsyncCompletions.create` (`openai.py:51-52`) then reassigns the class attribute to a wrapped function — mutating the one shared `AsyncCompletions` class object that every caller's `client.chat.completions.create(...)` resolves through via the instance's MRO, so it intercepts calls from code the SDK never imported or saw. The same `if _installed: return` / save-original / reassign-attribute shape repeats verbatim in `anthropic.py:30-33`, `bedrock.py:31-34`, `gemini.py:30-33` (each grepped and confirmed). This works because Python attribute assignment on a class object is unconditionally mutable at runtime, and `sys.modules` caching guarantees every `import openai` anywhere in the process — before or after `instrument()` runs — resolves to the same class object once patched.

**How TS's `wrap*` actually works: per-instance `Proxy`, never touches the class.** `wrapOpenAI()` (`instrumentations/openai.ts:64-69`) returns a `new Proxy(client, ...)` wrapping the one object instance the caller passed in; a `WeakMap<object, object>` (`openai.ts:33`) makes re-wrapping the same instance idempotent, and a `Symbol.for(...)` marker (`openai.ts:34`) detects cross-wrapper composition (`wrapXai(wrapOpenAI(client))`). Nothing in any of the ten other `instrumentations/*.ts` modules touches `OpenAI.prototype`, `Chat.Completions.prototype`, or any module-level export — the design is instance-scoped by construction, so a second `new OpenAI()` created anywhere else in the app, or one instantiated inside a nested dependency (e.g. inside LangChain's own OpenAI wiring), is invisible to it unless that exact instance is separately passed through `wrapOpenAI()`.

**The smoking gun that this is unimplemented work, not a blocked design: `detect-installed.ts` already holds the exact reference needed and throws it away.** `_safeRequire()` (`detect-installed.ts:21-46`) does a real `require(name)` (via `eval("require")` or, on Node ≥ 20.11 without a CJS `require` in scope, `process.getBuiltinModule("module").createRequire(import.meta.url)`, `detect-installed.ts:24,32-39`) and returns the actual resolved module namespace object — the same object Python's `install()` would monkey-patch a class on. But every call site discards it: `if (_safeRequire("openai")) result.openai = true;` (`detect-installed.ts:65`), repeated for all eleven frameworks (`:65,70,75,80,85,95,105,112,118,124,130`). The module reference containing `OpenAI.Chat.Completions.prototype` is live in memory at that exact line and is coerced to a boolean and dropped. `autoInstrument()` (`detect-installed.ts:138-140`) is a bare alias for `detectInstalledFrameworks()` — it does not call any `wrap*`, despite the name.

**Is CJS/ESM module immutability actually the blocker? No — not for prototype patching.** Node ESM does forbid *rebinding* a named export from outside the module (`import { OpenAI } from "openai"; OpenAI = X` throws `TypeError: Assignment to constant variable`-equivalent on the live binding) — but *mutating an object reached through* a still-bound import, e.g. `OpenAI.prototype.foo = wrapped` or `(await import("openai")).Chat.Completions.prototype.create = wrapped`, is ordinary object mutation and is legal in both CJS and ESM, because the binding is read-only, not the object it points to. Eden's own `_safeRequire` proves the object is reachable synchronously in both module systems already. What genuinely differs from Python is *reliable patch-before-first-use ordering across the whole module graph regardless of who imports first* — solved industry-side by `require-in-the-middle`/`import-in-the-middle` loader hooks (below), not by any change to how classes work. TS's current architecture (instance-`Proxy`) is best read as a deliberate choice to sidestep loader-hook complexity entirely, not a workaround for a hard blocker — at the cost of requiring per-call-site `wrap*()` calls.

### SDK self-health telemetry: observable on both sides, not silent

Neither SDK fails silently at the point of drop — both expose real counters, though coverage and documentation are uneven.

- **Python** exposes four `@property` getters at `client.py:1564-1587`: `.sent` (`_sent_total`), `.dropped` (`_dropped_total`, incremented at `client.py:629-637,949,987,996-1001`), `.sampled_out`, `.server_sampled_out` (parsed from the ingest response body's per-row outcome, not just HTTP status — comment at `client.py:598-604` explains a 100%-rejected batch still returns 2xx, so this field exists specifically so that failure mode isn't invisible). `doctor.py:183-217` actively uses `client.sent`/`client.failed` deltas (`sent0, failed0 = client.sent, client.failed` at `doctor.py:183`) to verify a real emit round-tripped, not just that the call didn't throw. None of `.dropped`/`.sampled_out`/`.server_sampled_out` are documented in `sdk/python/README.md` (grep: zero matches) — they exist and are exercised by the SDK's own diagnostic tool but are undiscoverable from the quickstart.
- **TS** exposes `droppedTotal` (`client.ts:590`, incremented at `:793,1330,1374` on queue/chunk-buffer overflow), `sampledOut` (`client.ts:578`), and `lastIngestHttpStatus` (`client.ts:596`, "Used by `runDoctor` to surface bad-key (401/403) without throwing"). `doctor.ts:150` does read `client.lastIngestHttpStatus`, but — unlike Python's doctor — never reads `droppedTotal` or `sampledOut`, so the CLI's own health report doesn't surface backpressure loss even though the counter exists. TS's README documents `droppedTotal` explicitly, twice (`README.md:19`: "counted on `droppedTotal`, not sent"; `README.md:386`: "count toward `droppedTotal` when the queue is full") — better quickstart discoverability than Python's on this specific axis, an inversion worth noting. TS has no `.sent`/`.failed` equivalent to Python's `_sent_total`/`_failed_total` (grep confirms no `sentTotal` field in `client.ts`) — a genuine, narrower gap: a TS user can see *how much* was dropped but not *how much* was successfully sent, so computing a loss rate requires instrumenting the app's own call count.
- Neither SDK emits these counters as their own telemetry event (e.g. a periodic `sdk_health` event back to eden) — both are pull-only (a getter/property the host app must read and act on itself, e.g. via a health-check endpoint or a metrics scrape), not push. That's a legitimate design (avoids infinite regress of instrumenting the instrumenter) but means an app that never reads `.dropped`/`droppedTotal` gets no signal at all despite the SDK tracking it correctly internally.

**Batching/flush behavior (Python, verified).** Defaults: `batch_size: int = 50`, `flush_interval_ms: int = 250`, `max_queue: int = 4096` (`config.py:137-142`). The background sender thread drains up to `batch_size` events per cycle (`client.py:824,844,872`); `flush()`/`flush_chunks()` exist for explicit sync (`client.py:653,896`); an `atexit` hook registers a best-effort final flush automatically (`client.py:30,1682-1684`, `_atexit_shutdown` at `client.py:1688`) — so a short-lived script doesn't need to remember to call `flush()` manually. Error surfacing is explicit where it matters: a dead sender thread raises `RuntimeError("eden sdk: sender thread failed to start; check the log for the underlying error")` (`client.py:536-539`) rather than silently queuing into a drain that will never happen — good practice, cited as a positive example, not a gap.

**Type safety.** `sdk/ts-ai` ships proper subpath type exports in `package.json` (`"types": "./dist/index.d.ts"`, plus per-instrumentation `.d.ts` for `openai`, `anthropic`, `vercel-ai`, `langchain`, `mastra`, `model_advisor` — `package.json:8-37`), which is good practice for a library whose main value-add is wrapping other people's typed clients. Not independently audited line-by-line for `any` leakage in this pass.

## How OpenTelemetry-JS auto-instrumentation actually works (the parity path)

Node has no built-in equivalent of Python's "reassign a class attribute" universality, so the OTel-JS ecosystem built two purpose-specific module-load interceptors that `@opentelemetry/instrumentation` (the base package every `@opentelemetry/instrumentation-*` package extends) composes over:

- **`require-in-the-middle` (CJS).** Source-verified (`nodejs/require-in-the-middle`, `index.js`): it does **not** patch `Module._load`; it saves and replaces `Module.prototype.require` itself (`this._origRequire = Module.prototype.require`, then `Module.prototype.require = function(id) {...}`), so every `require()` call anywhere in the process routes through the hook. For non-core modules it resolves the real file path via `Module._resolveFilename` and only invokes the registered `onrequire(exports, name, basedir)` callback once per module, using an `ExportsCache` keyed by a private `Symbol` stored directly on the cached `Module` object in `require.cache` — a deliberate choice so that if a user manually evicts `require.cache[id]` to force a reload, the hook's cache is evicted with it and re-patches on next require. A `patching` `Set` keyed by filename suppresses re-entrant `onrequire` calls triggered by circular `require()` chains during a module's own initial load. The callback receives and must return the (optionally mutated) `exports` object — this is the exact object Python's `install()` mutates a class attribute on; the mechanism is structurally the same operation, just reached via a hook instead of a plain `import`.
- **`import-in-the-middle` (ESM).** Source-verified (`nodejs/import-in-the-middle` README): ESM's static, asynchronous module graph has no synchronous load function to wrap, so this package instead registers a Node loader hook via `module.register()` (async, runs the hook on a separate thread, requires a `MessageChannel` handshake to synchronize with the app's own static imports — and **must be registered via `--import` before the app's own code is evaluated**, or static imports that already resolved are missed) or the newer synchronous `module.registerHooks()` (Node ≥ 22.22.3/24.11.1/25.1.0/26.0.0, runs on the app thread, no handshake needed). Once registered, `Hook()` targets specific specifiers and receives the module's namespace object to mutate **existing** exported bindings in place (`exported.foo += 1`-style rebinding of the namespace record) — explicit limitations from the README: it cannot add new exports, cannot alter a dynamically-`import()`-ed module after it has already loaded, and assumes a module's export-name set is stable across the process. Modules loaded via `require()` are untouched by this package — the two tools are non-overlapping and both are needed for full CJS+ESM coverage.
- **`@opentelemetry/instrumentation`'s `InstrumentationBase`.** Each concrete instrumentation subclasses `InstrumentationBase`, implements `init()` returning one or more `InstrumentationNodeModuleDefinition` objects (module name + semver range + `patch(moduleExports)`/`unpatch(moduleExports)` callbacks), optionally nests `InstrumentationNodeModuleFile` entries for files beyond the main export, and `enable()` wires a `require-in-the-middle` `Hook` (CJS) and an `import-in-the-middle` `Hook` (ESM, requiring the `--experimental-loader=@opentelemetry/instrumentation/hook.mjs` / `--import` flag at process startup) that both call the registered `patch()` on match. `patch()`/`unpatch()` internally use `this._wrap(obj, methodName, wrapperFactory)` / `this._unwrap(...)` — a shimmer-style helper that saves the original, replaces the property, and tags the replacement so `unwrap` can restore it — functionally identical to Python's save-original/reassign-attribute pattern, just generalized into a reusable helper instead of hand-rolled per module.
- **Even OTel-JS's own ecosystem doesn't have first-party OpenAI-Node coverage.** `open-telemetry/opentelemetry-js-contrib#2378` is an open issue requesting exactly this ("Add openai sdk" instrumentation) in the official contrib repo — the gap Traceloop's separately-maintained `@traceloop/instrumentation-openai` (in the `traceloop/openllmetry` monorepo) fills instead. This confirms eden would be writing original patch logic regardless of which loader-hook strategy it adopts; no off-the-shelf `@opentelemetry/instrumentation-openai` exists to depend on for the actual `chat.completions.create` patch body — only the module-loading plumbing (`require-in-the-middle`/`import-in-the-middle`) is reusable off the shelf.

## Concrete TS auto-instrumentation implementation plan

Two phases, deliberately separated because they have different risk/dependency profiles and the harder one is gated on real demand, not assumed need.

**Phase 1 — prototype-level patching, zero new dependencies, CJS-safe today, ESM-safe for any import that resolves before `instrument({ auto: true })` runs.** Change `detect-installed.ts`'s eleven `_safeRequire(...)` call sites (`:65,70,75,80,85,95,105,112,118,124,130`) to retain the resolved module object instead of discarding it into a boolean, matching the `AutoInstrumentResult` shape 1:1 with a parallel `detectedModules: Partial<Record<keyof AutoInstrumentResult, unknown>>`. Add one `_patchClass(moduleNs, path: string[], wrapperFactory)` helper per instrumentation module (mirrors Python's per-module `install()`) that walks to the known prototype method — e.g. for OpenAI, the exact target Python already proved out at `instrumentations/openai.py:51-52` (`AsyncCompletions.create`), reachable in the TS module object as `moduleNs.OpenAI.Chat.Completions.prototype.create` — and reassigns it to the same wrapper logic already implemented inside each `wrap*`'s `Proxy` `get` trap (refactor that trap body into a shared, reusable wrapper function rather than duplicating it). Add `instrument({ auto: true })` (or `autoInstrument()` promoted from detection-only to action) in `instrument.ts:50-58` that, for each `detected.<x>`, calls the matching `_patchClass` instead of only returning an unused `wrap*` factory. Idempotency: reuse Python's `_installed`-module-global-flag pattern (`openai.py:31-33`) rather than TS's current `WeakMap<instance>` pattern, since patching now targets a class, not an instance. This closes Recommendation 2 below without touching CJS/ESM loader mechanics at all, because it operates purely on the object `_safeRequire`/`createRequire` already resolves synchronously — no `require-in-the-middle` dependency needed for this phase.
**Limitation to document, not silently ship past:** Phase 1 only intercepts calls made through the shared prototype. It will not intercept instances constructed with an already-bound closure-captured method reference (e.g. `const { create } = client.chat.completions; create(...)` — destructuring before `instrument({ auto: true })` runs binds `create` to the *pre-patch* function) or any provider SDK that hands out closures instead of prototype methods (verify per-provider before enabling; the eleven `wrap*` modules already encode the exact per-provider shape needed since the `Proxy` `get` trap has to intercept the same call surface).

**Phase 2 — loader-hook-based patching (only if Phase 1's ordering caveat proves to matter in practice).** Take a direct dependency on `require-in-the-middle` (CJS: register a `Hook(['openai', '@anthropic-ai/sdk', ...])` at `instrument()` call time, patching on first `require()` regardless of import order, replicating the `ExportsCache`+`patching Set` re-entrancy guards described above so a future in-house implementation doesn't reinvent — and mis-implement — circular-require handling) and, for ESM apps, `import-in-the-middle` via `module.registerHooks()` where available (Node ≥ 22.22.3) falling back to `module.register()` — which requires eden to document a `--import @eden-ai/sdk/register` (or equivalent) startup-flag contract, exactly mirroring OTel-JS's own documented `--import`/`--experimental-loader` requirement, since ESM hook registration must happen before the app's own static imports evaluate. This is a real DX cost (a required startup flag, not just an SDK call) that Phase 1 avoids entirely — which is why it should stay opt-in and Phase 2, not the default path.

## Recommendations

1. **Promote `agent_id`/`agentId` from optional to required client config — sequenced strictly after portal-first agent registration ships**, per `INDEX.md` Phase C, item 14 (`INDEX.md:660-661`: *"Portal-first agent registration + `agent_id` required promotion (`features/09`) — already cheap, fully-plumbed in both SDKs."*). This doc's own source-level verification (above) confirms the premise INDEX.md relies on: the field, env var, header, and auto-stamp plumbing all already exist symmetrically in both SDKs, so this is a validation-strictness change (raise instead of silently omit) plus a docs/README update, not new plumbing. Making it required before the portal flow exists would strand every current user with no way to obtain a valid id — the sequencing is load-bearing, not a nicety.

2. **Close the TS `instrument()` auto-patch gap — concrete plan above, Phase 1 first.** Ship the zero-new-dependency Phase 1 (prototype-level patching reusing the module reference `_safeRequire` already resolves and discards at `detect-installed.ts:65-130`) before considering Phase 2's `require-in-the-middle`/`import-in-the-middle` loader-hook approach, which adds a real DX cost (a required `--import` startup flag for ESM apps, mirroring OTel-JS's own documented constraint). This is the single biggest remaining onboarding-friction gap between eden's own two SDKs and puts TS at parity with Python's `eden.init()` one-liner and with Traceloop/Langfuse's zero-per-client-wiring paths — and, per the mechanism analysis above, it is unimplemented work, not a CJS/ESM technical blocker.

3. **Document `agent_id`/`agentId` as a top-level `configure()`/init parameter in both READMEs.** It's currently invisible outside the session-helper example; fixing this is a five-minute change that should land alongside (not blocking) recommendation 1.

4. **Do not add OTel `gen_ai.*` attribute support in this pass.** It's a real gap (zero matches, confirmed) and worth a future ticket, but it's a bigger lift (schema mapping both directions across two SDKs plus the OTLP bridge) than the other three items here and isn't blocking any near-term feature; noting it is enough for this review.

5. **Rename `detect-installed.ts`'s `autoInstrument()` or make it warn — near-zero cost, ships independently of recommendation 2.** The function (`detect-installed.ts:138-140`) is a bare alias for `detectInstalledFrameworks()`; it detects and returns nothing patched. A name that promises Traceloop/Python-style zero-touch coverage but silently delivers a boolean map is worse than no function at all — a developer who calls it and moves on has no compiler, lint, or runtime signal that their app is untraced. Either rename it to something honest (`detectFrameworks()`) or have it log a one-time warning that it is detection-only. This is strictly cheaper than, and can land ahead of, the Phase 1 patching work in recommendation 2.

## User Experience & Value

**Who the user is and what "done" looks like.** The user is a developer wiring observability into an existing app that already calls OpenAI/Anthropic/Bedrock/etc. directly or through a framework (LangChain, LlamaIndex, Mastra...). The value proposition is standard for this category: install a package, add a small number of lines, and every LLM call — including ones buried inside a framework's internals — starts producing a trace in eden with no change to business logic. The bar for "done" is exactly what Python's `instrument()` already clears: interception at the shared class/prototype level, not just the call sites the developer remembers to wrap.

**Python: the integration flow is genuinely close to best-in-class, once the deprecation asterisk is accounted for.** `pip install eden-sdk` → `eden.configure(org_id=..., api_key=...)` → `eden.instrument()` → first trace appears with zero further code changes, for any of thirteen supported frameworks (`__init__.py:188-253`). This is real class-level monkey-patching (`chat_completions.AsyncCompletions.create = wrapped`, `openai.py:52`) — it intercepts calls from code the SDK never imported, which is the actual bar for "auto-instrumentation," not a stub. The literal one-call form, `eden.init(...)`, still works but is marked back-compat in its own docstring (`__init__.py:288-289`); the currently-recommended path is the two-call `configure()`+`instrument()` shape, same call-count as TS — Python's real advantage over TS is that its second call needs zero per-provider, per-client wiring, not that it has fewer calls (see table footnote above).

**The one first-run failure mode that actually matters — forgetting `org_id` — is silent on the Python side today, contrary to what the code's own `ValueError` and TS's own source comment would suggest.** `EdenConfig.ingest_url()` raises on a missing `org_id` (`config.py:216`), but the only call site is inside the background sender thread (`client.py:1238`), caught by a broad `except Exception: logger.warning(...)`. `configure()` performs no eager validation. A misconfigured integration configures cleanly, instruments cleanly, and runs the app normally — the only way to discover the problem is to run `python -m eden_sdk.doctor` or read the undocumented `.dropped`/`.failed` counters. TS, by contrast, emits an unconditional, synchronous `console.warn` at client-construction time (`client.ts:280-295`) — no logging configuration required to see it. This is the reverse of the ranking implied by TS's own in-source comment ("The Python SDK raises a clear ValueError in the same situation") and worth fixing: promote the `org_id` check to run eagerly inside `configure()` itself, not just deep in the sender thread.

**TypeScript: the components for best-in-class DX exist, but the assembly leaves a manual-wrap tax on every call site.** A new Node integration writes `configure({ orgId, apiKey })` then must call the matching `wrap*()` — `wrapOpenAI(new OpenAI())`, `wrapAnthropic(...)`, etc. — once per client *instance*, including instances constructed inside a dependency's own internals (e.g. LangChain's internal OpenAI client), which are invisible to this pattern by construction (the `Proxy` wraps one object; nothing touches `OpenAI.prototype`). For an app with LangChain, direct OpenAI calls, and a Bedrock fallback, that's three wrap call sites to remember across three files, with no compiler or lint signal if one is missed — a silently-untraced code path, no error, no warning. Compounding this, `detect-installed.ts` exports a function literally named `autoInstrument()` (`detect-installed.ts:138-140`) that does not auto-instrument anything — it's a one-line alias for `detectFrameworks`-style detection, returning a boolean map while leaving the app exactly as untraced as before. A developer who trusts the name gets silently misled (Recommendation 5, above).

**Docs are a genuine strength, with one specific, fixable gap.** Both READMEs (`sdk/python/README.md`, 481 lines; `sdk/ts-ai/README.md`, 440 lines) are substantive and accurate against source — env var tables, framework-support matrices, and TS's explicit documentation of the `droppedTotal` backpressure counter are all real, verified DX assets. The public docs site (`docs/docs/quickstart.mdx`, `docs/docs/reference/sdk-python.md`, `docs/docs/reference/sdk-typescript.md`) has zero dangling Go/Rust references post-deletion. The one clear gap, confirmed independently in this pass: `agent_id`/`agentId` is invisible as a top-level `configure()` option in either README, appearing only inside the unrelated `begin()` session-helper example (Recommendation 3, above).

**Bottom line.** The building blocks for a best-in-class onboarding experience already exist on both sides — real class-level monkey-patching proven out in Python, a correctly-designed (if incompletely wired) detection layer in TS, real self-health counters, and a real diagnostic CLI on both sides. What's missing isn't new engineering surface area, it's finishing two already-scoped threads: making Python's default first-run experience fail loud instead of fail quiet on the single most common misconfiguration, and closing the TS auto-patch gap (Recommendation 2) so `wrap*()` becomes an escape hatch for edge cases rather than the mandatory path for every client instance in the app.
