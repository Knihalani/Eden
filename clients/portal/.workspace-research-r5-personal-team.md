## 1. Thesis

Eden models “solo” as an **organization row with `is_personal=true`**, not Clerk’s Personal Account. The portal already soft-hides the main team jobs (invite, SCIM tab access, ownership transfer, org-wide 2FA enforcement) when that flag is set. The **target** (Ambition A / R10 **M5** / R9 mode table) is stricter and more productized:

1. **Zero team-only chrome leaks** on personal workspaces.  
2. **Members teaches upgrade** (no invite spam) with a real path to a team workspace.  
3. **Shared mode helpers** (`workspace-mode` / `use-org`) drive hide/show + “workspace” copy — not ad-hoc `Boolean(org?.is_personal)` in every leaf.  
4. **Overview CTA** for personal→team (M11 / S6) — not only a muted banner on Members.

Today: gates exist and are mostly correct; **upgrade path, overview CTA, centralized helpers, and copy/⌘K scent** still leak or dead-end vs target.

## 2. Data model — `is_personal`

| Layer | Behavior |
|-------|----------|
| **DB** | Migration `046_free_only_default_plan.py`: `organizations.is_personal BOOLEAN NOT NULL DEFAULT false`. Backfill: single-member orgs (`COUNT(org_members)=1`) → `true`. Billing/quotas do **not** key off this flag; they use `org_resource_limits.plan_name`. |
| **Create** | `POST /orgs` (`src/eden/api/routes/orgs.py`): first membership for the user → `is_personal=true`; subsequent creates → `false` (team). Schema probe via `organizations_have_is_personal` (pre-046 safe). |
| **API surface** | `/auth/me` and org list include `is_personal` when column exists (`auth.py`, `orgs.py`). |
| **Portal type** | `Organization.is_personal?: boolean` in `src/lib/types.ts` — comment: soft-hides invite/SCIM/transfer. Preserved through `organizationFromCreate` / dehydrate. |

**Important distinction vs Clerk:** Sidebar uses Clerk `<OrganizationSwitcher hidePersonal />`. That hides Clerk’s **Personal Account** (user operating with no org), **not** Eden’s personal workspace org. Eden personal orgs still appear in the switcher as normal Clerk organizations.

## 5. Visibility gaps vs target (M5 / M11 / M13)

Ranked for Wave 1–2 / 4 / 8 work.

### G1 — Dead-end personal→team CTA (critical)

Members (and SCIM toast) say **create a team organization under Organization settings**, but live `OrgTab` only shows **Create Organization** when `!org` (orgless). With an active personal org, Organization settings shows identity + danger zone — **no “Create team workspace” action**.

**Peer pattern:** Vercel / Clerk: create team from **switcher** or explicit Settings CTA; GitHub: create org / move work — never a banner that points nowhere.

**Target fix direction (research only):** Primary CTA on personal overview + Members banner linking to create-team (or Clerk `createOrganization`); optional secondary “keep personal”. Do not convert personal row in place unless product explicitly ships a migrate path (GitHub deprecated convert-user→org; prefer create + optional transfer).

### G2 — No Workspace overview personal→team composition (M11 / S6)

Default Settings landing is still **Organization tab**, not an overview composition with plan chip + personal→team CTA. R9/R10 call this out; not shipped.

### G3 — No centralized `workspace-mode` helper (M13)

Gates are duplicated: `isPersonalOrg` / `isPersonal` / `org.is_personal` across `settings/page.tsx`, members, org, security, transfer. No shared helper for:

- `isPersonalWorkspace(org)`
- `canShowTeamChrome(org)`
- copy keys (“personal workspace” / “team workspace”)
- freeze assertions

### G4 — ⌘K / nav scent advertises team jobs on personal

`SETTINGS_TAB_COMMANDS` in `nav-commands.ts` (not mode-gated):

- Organization: “…**and ownership transfer**.”  
- Members: “**Invite teammates** and manage membership.”  
- **SCIM** is a first-class command (`/settings?tab=scim`, “Directory provisioning…”) — personal users can open it from ⌘K and only then hit the mode toast. That is a **promo leak** vs M5 / S16 (hide team-only chrome; don’t advertise).

Ghosts (`roles` / `sso`) are correctly omitted from the palette; SCIM / invite / transfer scent is not.

### G5 — Members banner is explain-only, not act

Banner text exists (good vs “invite spam”), but:

- No button / link to create team (and Org tab can’t fulfill the promise — G1).  
- Empty table still uses team-flavored framing when not `canInvite` (`emptyDescription` undefined only when `!canInvite` — OK; empty title “No members yet” is fine for solo).

### G6 — Legacy duplicate surfaces

`members-settings.tsx` / `org-settings.tsx` mirror personal gates but are **not** the live hub tabs (`MembersTab` / `OrgTab` are). R10 S15: dedupe risk — mode fixes must land on live tabs; orphans can drift.

### G7 — Stale test expectation (W7-D)

`w7-d-opportunistic.test.ts` expects:

```ts
isPersonalOrg && (id === "scim" || id === "sso")
```

Live code only gates **SCIM** in `canAccessTab`; **SSO** is handled via `GHOST_TABS` for everyone. `w6-1` already documents “SSO is a ghost tab.” Freeze/mode tests should assert the R9 split (mode soft-hide vs ghost), not the old combined predicate.

### G8 — Label / chrome inconsistencies

| Place | Leak |
|-------|------|
| `NoOrgState` | “Create organization” vs “workspace” titles |
| Invite accept | “organization switcher” |
| Org switcher | No “Personal” badge; Eden personal looks like any team |
| Marketing | Correctly distinguishes personal vs org seat caps — product chrome doesn’t mirror that literacy |

### G9 — What does *not* need hiding on personal (keep)

Account, API keys, Billing, Security (user 2FA), archive/delete personal workspace, Advanced data plane (gateway/PII/retention) — R9 says keep keys/account/billing first-class. Org-wide 2FA enforcement correctly soft-hidden (team roster job).

## 6. Peer upgrade patterns (steal grammar)

### 6.1 Scope split (all peers)

| Product | Solo / me | Us | Surface |
|---------|-----------|----|---------|
| **Stripe** | Personal settings | Account / Team & security | Product settings |
| **Vercel** | User prefs | **Team** (Hobby team = solo-capable workspace) | Project settings |
| **Linear** | Account | **Workspace** admin | Team (product) settings |
| **GitHub** | User account | **Organization** | Repo |
| **Clerk** | Personal Account (optional) | Organization | App |

Eden already chose **org-centric** (`hidePersonal` on Clerk). Solo is an org flag — closer to **Vercel Hobby team** / **GitHub org with one owner** than Clerk Personal Account.

### 6.2 How peers unlock “team”

| Pattern | Who | Steal for Eden? |
|---------|-----|-----------------|
| **Create a new team/org from switcher** | Vercel, Clerk, Linear (create/join workspace) | **Yes — primary.** Matches `POST /orgs` second-create → `is_personal=false`. |
| **Upgrade same workspace plan** (Hobby→Pro without new container) | Modern Vercel | Optional later for **billing**; does not unlock multi-seat by itself in Eden’s model. |
| **Convert personal account → org** | GitHub (deprecated 2026) | **No** — peers moved away; prefer create/move. |
| **Move work into org** | GitHub Move work | Future data migration; not Wave 0. |
| **Invite-gated empty Members** | Linear / Vercel | Hide Invite; show why + path to unlock (role **or** plan/mode). Eden uses mode, not only role. |
| **SCIM / SSO plan-gated** | Linear Enterprise Security | Hide from solo/personal; deep-link quiet deny — Eden SCIM already mode-gated. |

### 6.3 Steal-for-Eden (personal→team)

1. **One primary unlock CTA:** “Create team workspace” (name → `POST /orgs` → `is_personal=false` → `setActive`).  
2. **Explain, don’t tease:** Members banner + overview line state what unlocks (invites, transfer, SCIM).  
3. **Keep personal row:** Don’t flip `is_personal` when a second member is invited unless product defines migrate-in-place; today invites are blocked, so personal stays solo by construction. (Backfill marked single-member as personal; no live demotion path when a team gains members — note as open question if invites ever allowed on personal.)  
4. **Switcher literacy:** Optional badge “Personal” on Eden personal orgs; create-team entry in switcher and/or Settings.  
5. **⌘K mode-aware descriptions:** Personal → “Workspace identity & archive”; Team → transfer/invite language.

## 9. Open questions (product)

1. **In-place convert?** Flip `is_personal→false` when creating a “team” from the same org vs always create a second org? Peers prefer create/move; Eden create API already treats 2nd org as team.  
2. **Clerk createOrganization vs Eden `POST /orgs`?** Switcher create must stay Eden-synced (webhook / local create) so `is_personal` stays correct.  
3. **Should personal orgs leave the switcher labeled?** Helps literacy; risk of clutter.  
4. **If a solo org was backfilled `is_personal` but later grows members via API/SCIM outside portal** — does flag auto-clear? No portal path today; backend policy unclear.  
5. **Billing:** personal vs org free caps are marketing-visible; should overview plan chip mirror that for personal mode?
